## 쟁점

`docs/DESIGN.md`가 **"강조색은 한 화면에 한 자리다"**라고 정했는데, 세어보면
한 자리가 아니다. 015·016·006에서 세 번 나왔다.

이번에 다시, **두 테마로** 셌다(13 mini · 50/34).

| 화면 | 강조로 칠해진 것 | 무엇                                             |
| ---- | ---------------- | ------------------------------------------------ |
| 홈   | **4**            | 진행중 알약 · 진행 막대 · `뜨기` · 활성 탭 글자  |
| 목록 | **3**            | `+` · 진행중 알약 · 활성 탭 글자                 |
| 상세 | **5**            | 알약 · 막대 · `뜨기` · **`완성`** · 활성 탭 글자 |
| 뜨기 | 0                | —                                                |

라이트와 다크가 같은 수다.

**고칠 것이 코드인지 문장인지**가 이 스레드의 질문이었다.

---

## 답: 둘 다 틀렸다

### 문장의 **글자**가 틀렸다

`:101`은 강조가 **먹색이던 때** 쓴 문장이다. 그때는 넷이 다 무채라 "한 자리"가
지켜지는 것처럼 보였다. 015가 색을 쑥으로 옮기면서 그 문장이 실제로 무엇을
요구하는지가 드러났다 — 그리고 **요구할 수 없는 것**을 요구하고 있었다.

넷은 하는 일이 다르다.

| 칠한 것        | 말하는 것           |
| -------------- | ------------------- |
| 상태 알약      | "이게 진행중"       |
| 진행 막대      | "여기까지"          |
| 활성 탭 글자   | "지금 여기"         |
| **꽉 찬 단추** | **"이걸 누르세요"** |

앞의 셋을 없애면 잃는 것이 있다. 특히 알약은 `DESIGN.md:119`가 "진행중은
**유일하게 꽉 찬 알약**"이라고 따로 정해뒀다 — `:101`을 글자대로 지키면 `:119`와
충돌한다. **문서가 자기 자신과 부딪히고 있었다.**

### 코드에도 진짜 위반이 하나 있었다

원칙 1이 걱정한 "경쟁"은 **같은 일을 두고 둘이 다투는 것**이다. 넷 중 실제로
그런 것은 하나뿐이었다 — **상세의 `뜨기`와 `완성`.** 둘 다 꽉 찬 강조 단추이고,
넓은 화면에서는 `뜨기`가 본문 단에, `완성`이 옆 단에 **같은 높이로 나란히**
선다(011의 1920px 화면에서 눈으로 확인). 어느 쪽이 "지금 누를 것"인지 화면이
말하지 못한다.

### 그래서

**문장**: `:101`을 다시 썼다.

> **꽉 채운 강조 단추는 한 화면에 하나다.** 그 하나가 "지금 눌러야 할 것"이다.
> … 상태 알약·진행 막대·활성 탭 글자는 **세지 않는다.**

**코드**: 상태 전환 단추(`START`·`RESUME`·`FINISH`)가 **`뜨기`가 있을 때는
주 단추가 아니다.** `뜨기`가 주동선이고(001 결정 1), 없을 때 — 계획중이라 아직
셀 것이 없을 때 — 만 이 셋이 그 자리를 받는다.

| 화면         | 고치기 전 꽉 찬 강조 단추 | 고친 뒤         |
| ------------ | ------------------------- | --------------- |
| 홈           | 1 (`뜨기`)                | 1 (`뜨기`)      |
| 목록         | 1 (`+`)                   | 1 (`+`)         |
| 상세(진행중) | **2** (`뜨기`·`완성`)     | 1 (`뜨기`)      |
| 상세(계획중) | 1 (`뜨기 시작`)           | 1 (`뜨기 시작`) |
| 상세(완성)   | 0                         | 0               |
| 뜨기 모드    | 0                         | 0               |

## 관문 — `scripts/measure-accent.mjs`

017의 완료 기준 둘째가 "**개수를 세는 방법이 남는다**"였다. 이게 그것이다.

| 관문 | 보는 것                                               |
| ---- | ----------------------------------------------------- |
| A    | 꽉 채운 강조 단추가 한 화면에 **최대 하나**           |
| B    | 그 하나가 화면에서 **가장 큰 강조면**이다             |
| C    | `docs/DESIGN.md`의 문장과 관문이 **같은 것을 말한다** |

**C가 절반이다.** 015가 남긴 교훈이 "문서와 코드가 각자 맞다고 믿으면 둘 다
틀린다"였다. 관문이 `DESIGN.md`의 문장을 **문자 그대로** 찾는다 — 문장을 고치면
관문이 깨지고, 그때 둘을 같이 보게 된다.

**B가 있는 이유.** A만 있으면 "강조 단추 하나"를 **작은 것**으로 만들어 통과할
수 있다. `뜨기`를 보조로 내리고 작은 `카드로 공유`를 주 단추로 올리면 A는
통과하는데 화면은 더 나빠진다. B가 그걸 잡는다.

**`--accent`를 상수로 읽지 않는다.** 실제로 계산된 색과 비교한다 — 상수끼리
비교하면 015가 통과했던 방식이 된다.

---

## 세는 관문의 함정 — 이 관문이 한 번 조용히 통과했다

관문을 다 짜고 깨뜨려보다가, `src/index.css`에서 `--color-accent`가 없는 이름을
가리키게 바꿨다. **강조색 토큰이 통째로 깨진 상황**이다.

관문은 이렇게 찍었다.

```
  ○ [dark] 뜨기 — 단추 0개 [] · 모든 강조면 0개

모든 관문 통과
```

**세는 관문의 고유한 함정이다 — 셀 것이 사라지면 세기는 늘 성공한다.** "최대
하나"는 0개일 때 가장 잘 지켜진다.

막았다. 홈에는 `뜨기`가 **언제나 있고**(006이 그렇게 정했고 007의 관문 B1이
지킨다), 그러니 홈에 강조면이 하나도 없으면 화면이 아니라 토큰이 깨진 것이다 —
관문 실패(1)가 아니라 **환경 문제(2)**로 끝낸다. 어느 화면에서도 강조면을 못
봤을 때도 같다.

이게 `WORKLIST.md`가 말한 "반복되는 실패 하나"의 또 다른 얼굴이다. 007의 A3는
"잉크가 있는데 안 보이는" 경우였고, 여기는 "셀 것이 없어서 세기가 성공하는"
경우다.

## 깨뜨려본 것

다섯 번 깨뜨렸고 **다섯 번 다 물었다.** 그중 한 번은 **관문을 고쳐야** 물었다.

| 깨뜨린 것                                       | 기대   | 실제                                                                     |
| ----------------------------------------------- | ------ | ------------------------------------------------------------------------ |
| 상태 전환 단추를 늘 primary로 되돌림            | A 실패 | 종료 1 — 두 테마 모두 `상세에 꽉 찬 강조 단추가 2개다 — 뜨기, 완성`      |
| `뜨기`를 보조로, 작은 `카드로 공유`를 주 단추로 | B 실패 | 종료 1 — `가장 큰 강조면이 뜨기 시작(3526)인데 단추는 카드로 공유(1936)` |
| `DESIGN.md`의 문장만 고침                       | C 실패 | 종료 1 — `문장을 찾지 못했다 — 관문의 \`문장\`도 같이 고친다`            |
| `--color-accent`를 없는 이름으로 (처음)         | 2 기대 | **종료 0 — 조용히 통과했다.** 위 절 참고                                 |

두 번째 줄이 B를 넣은 이유를 그대로 보여준다 — A만 있으면 통과할 화면이다.

### 치환이 두 번 빗나갔다

`<Button block …>`의 들여쓰기를 잘못 세어 문자열 치환이 아무것도 안 했다.
`assert`가 잡아서 파일이 안 바뀌었고, 줄 번호로 바꿔 다시 했다. 011·012에서
같은 일이 있었다 — **깨뜨리기는 깨뜨렸다는 것 자체를 확인해야 한다.**

## 013에 넘기는 것

013이 시각 언어를 정할 때 이 관문이 이미 서 있다. **색을 바꿔도 "꽉 찬 강조
단추는 하나"는 그대로 성립해야 한다** — 013이 강조를 다른 색으로 옮기면 관문은
새 색을 그대로 읽는다(상수로 안 박았다). 문장을 고치려면 관문의 `문장`도 같이
고친다.

## 남는 것

- **`DESIGN.md:119`("진행중은 유일하게 꽉 찬 알약")는 그대로 둔다.** 알약은
  이제 세지 않으므로 `:101`과 부딪히지 않는다. 알약이 `뜨기`와 경쟁하는지는
  B가 본다 — 지금은 알약이 훨씬 작아 통과한다.
- **`뜨기` 모드에는 강조 단추가 하나도 없다.** `+1`이 강조가 아닌 것은 012가
  정한 것이고(밤에 조명 판이 된다), 그 화면의 주 동작은 색이 아니라 **크기와
  그림자**로 말한다. A는 "최대 하나"라 0개도 통과한다 — 다만 그게 의도인지는
  013에서 시각 언어를 정할 때 한 번 더 본다.

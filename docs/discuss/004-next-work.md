## 쟁점

003이 main에 머지됐고 대기 중인 일이 셋이다. **무엇을 먼저 하고, 브랜치를 어떻게
이름 지을 것인가.**

이 스레드는 논쟁이 아니라 **차례를 넘기는 자리**다. `scripts/new-work.sh`가
"새 브랜치는 기획이 연다 — 다음에 무엇을 할지 정하는 자리가 그 작업의 이름을
짓는다"고 못 박고 있어서, 검증이 이름을 지으면 기획의 판단을 뺏는다. 그래서
후보만 늘어놓고 순서·범위·이름은 기획이 정한다.

틀리면 잃는 것: 순서를 잘못 잡으면 뒤엣것이 앞엣것을 다시 만들게 한다. 예를 들어
목록 카드를 먼저 만들고 나서 안전영역 관문을 실물로 다시 재면, 카드가 관문을
넘겨서 방금 만든 것을 줄여야 할 수 있다.

## 선택지

**A. `REDESIGN.md` §5 1단계 — 프로젝트 목록 카드를 이미지형으로**
막는 것이 없다. 강조색(쑥 `#3f5d48`)과 사진 상한(`aspect-[4/3]`)이 003·강조색
결정으로 정해졌다. 003이 "지금 값은 예산이지 결과가 아니다. 005·006에서 실제
카드가 생긴 뒤 다시 돌려야 한다"고 남겼으므로, 이걸 하면 그 재측정도 함께 온다.

**B. 하단 내비 12px 겹침**
`src/routes/__root.tsx:60`의 `main`이 `pb-20`(80px)인데 `:111`의 `nav`는
`pb-safe`라 58+34=92px다. 탭바가 있는 **모든 화면**에서 본문 마지막 12px이 깔린다.
003에서 대리가 "이견이 없으니 스레드를 열지 말고 003 병합 뒤 새 작업으로 연다"고
정해뒀다. 방향도 적혀 있다 — `pb-[calc(5rem+env(safe-area-inset-bottom))]`.

**C. 감시자가 다른 브랜치의 스레드를 못 본다**
`scripts/watch-discuss.sh:84`가 HEAD의 브랜치를 읽고 `:101`이 `origin/$BRANCH`만
본다. 003이 `fix/safe-area-cap`에 열렸을 때 검증은 옛 브랜치에 있어서 못 봤고,
사람이 "모니터 안 되고 있어?"라고 물어서 찾았다. **지금도 같다** — 기획이 새
브랜치를 열면 다른 자리는 각자 옮겨오기 전까지 못 본다.

### 구현 · 2026-08-29 · 1왕복

**고쳤다. 잰 값을 남긴다.**

`src/index.css`에 `.pb-nav` 유틸을 두고 `src/routes/__root.tsx:65`의 `pb-20`을


빌드되는 형태로 확인해야 한다"고 짚은 자리다. `index.css`의 `@layer utilities`에는

### 측정에서 걸린 것 — 관문을 둘로 갈랐다

처음 재니 **고친 뒤에도 80px**로 나왔다. 고친 것이 안 먹은 줄 알았는데 원인은
측정 쪽이었다. 안전영역 시뮬레이션이 `.pb-safe`만 덮는데 `.pb-nav`는 `env()`를
직접 쓰므로, 헤드리스에서 `env()`가 0이라 80 + 0 = 80이 된 것이다.

**헤드리스는 `env(safe-area-inset-*)`를 에뮬레이션할 수단이 없다.** 그래서 관문을
둘로 갈랐다.

| 관문 | 무엇을 보는가                                                              | 시뮬레이션인가                                        |
| ---- | -------------------------------------------------------------------------- | ----------------------------------------------------- |
| 규칙 | `.pb-nav`가 실제로 `calc(5rem + env(safe-area-inset-bottom))`로 생성되는가 | **아니다.** 브라우저가 읽는 CSS를 그대로 읽는다       |
| 산술 | 그 안전영역 값에서 padding ≥ 탭바 높이인가                                 | **맞다.** `.pb-safe`와 `.pb-nav`를 같은 값으로 덮는다 |

산술 관문만으로는 공식이 맞다는 증거가 안 된다 — 내가 넣은 값을 내가 다시 읽는
꼴이기 때문이다. 규칙 관문이 그 자리를 메운다. 실제로 생성된 규칙은 이렇다.

```
.pb-nav { padding-bottom: calc(5rem + env(safe-area-inset-bottom)); }
```

### 검증 · 2026-08-29 · 1왕복

**나갔다.** 고친 것이 맞고, 잰 것도 맞다. 다만 **묻는 것 둘 다 답이 바뀐다** — 산술
관문은 시뮬레이션을 그만둘 수 있고, `5rem`은 그대로 두되 관문에서 빼야 한다.

#### 확인한 것

구현의 관문을 그대로 돌렸다. 종료코드 0, 표가 재현된다(규칙 통과, 고치기 전
12px·12px 가림, 고친 뒤 셋 다 0px). `type-check`·`lint`·`build` 통과, 테스트
595개 전부 통과. 범위도 지켰다 — `git diff main...HEAD --stat` 기준 손댄 것은
`src/index.css`·`src/routes/__root.tsx`·`scripts/measure-bottom-nav.mjs`와 이 문서,
그리고 `docs/discuss/README.md`의 스레드 목록 한 줄이다. 기획의 "안 할 것" 셋
(목록 카드·홈 첫 카드·감시자)에 닿은 것이 없다.

#### 1. 산술 관문 — 시뮬레이션을 그만둘 수 있다

**"헤드리스는 `env(safe-area-inset-*)`를 에뮬레이션할 수단이 없다"가 사실이
아니다.** 이 크로미움에 CDP `Emulation.setSafeAreaInsetsOverride`가 있다.

```js
const cdp = await ctx.newCDPSession(page);
await cdp.send("Emulation.setSafeAreaInsetsOverride", {
  insets: { top: 50, left: 0, bottom: 34, right: 0 },
});
```

클래스를 하나도 덮지 않고, 브라우저가 `env(safe-area-inset-bottom)`를 진짜로 34px로
읽는다. 그 상태에서 다시 쟀다. `env(bottom)` 열은 페이지 안에
`height:env(safe-area-inset-bottom)`짜리 탐침을 넣어 읽은 값이다.

| 기기                       | env(bottom) | main padding | 탭바 | 여유 |
| -------------------------- | ----------- | ------------ | ---- | ---- |
| 헤드리스 390×844 · 0/0     | 0px         | 80px         | 58px | 22px |
| 아이폰14 390×844 · 47/34   | **34px**    | 114px        | 92px | 22px |
| 13 mini 375×812 · 50/34    | **34px**    | 114px        | 92px | 22px |
| 15 Pro Max 430×932 · 59/34 | **34px**    | 114px        | 92px | 22px |

**구현의 시뮬레이션은 정직했다.** 114/92라는 숫자가 진짜 `env()`에서 한 자리도
틀리지 않는다. 그러니 이번 판정은 이대로 서고, 실기기 확인 없이 나간다.

그래도 **관문은 바꾸는 게 낫다.** 이유는 이번 숫자가 틀려서가 아니라 다음번에
틀려도 모르기 때문이다. `scripts/measure-bottom-nav.mjs:65`는 `.pb-nav`를
`calc(5rem + ${b}px)`로 덮는데, 여기 **`5rem`이 스크립트 안에 박혀 있다.** 누가
`src/index.css:245`의 밑값을 `3rem`으로 줄이면 실제 화면은 82px가 되어 92px 탭바에
10px 깔리지만, 산술 관문은 여전히 114px을 재고 통과한다. 지금은 규칙 관문의
`rule.includes("5rem")`이 그 자리를 막고 있다 — 그런데 그건 **묻는 것 2의 답을
관문에 못으로 박아둔 것**이다. 나중에 밑값을 재서 고치면 관문이 엉뚱한 이유로 깨진다.

진짜 `env()`를 쓰면 관문이 하나로 줄고 문자열 대조가 사라진다. 재는 것은 하나뿐이다
— **본문 하단 padding ≥ 탭바 높이.** 밑값이 몇이든, 유틸 이름이 무엇이든 참이어야 하는
관계다.

**실기기 확인은 이 결함에 대해서는 답을 못 준다.** `docs/DEVICE-TEST.md:3`의 대상은
안드로이드 크롬이고, 우리가 재는 34px은 아이폰 홈 인디케이터 값이다. 안드로이드
브라우저 탭에서는 아래쪽 inset이 0으로 오는 경우가 흔해서 **조건 자체가 재현되지
않을 수 있다**(내가 여기서 확인할 수 없는 부분이다). 그래서 실기기를 기다리는 것은
증거를 늘리는 게 아니라 판정을 미루는 것이 된다.

#### 2. `5rem` — 재보니 밑값은 그대로 두는 게 맞다

"내가 재서 정한 값이 아니다"는 맞는 말이지만, 재보니 **바꿀 이유가 없다.** 두 가지를
쟀다.

**글자를 키워도 여유는 줄지 않고 늘어난다.** 걱정한 "탭바가 두꺼워지면"이
글자 확대로는 오지 않는다. 탭바 알맹이는 배율당 +9px씩 자라는데 `5rem`은 rem이라
+20px씩 자란다. 13 mini · 50/34에서:

| 배율  | 탭바 알맹이 | 탭바  | main padding | 여유 |
| ----- | ----------- | ----- | ------------ | ---- |
| 1×    | 58px        | 92px  | 114px        | 22px |
| 1.25× | 67px        | 101px | 134px        | 33px |
| 1.5×  | 76px        | 110px | 154px        | 44px |
| 2×    | 94px        | 128px | 194px        | 66px |

**`rem`으로 쓴 것이 여기서 값을 한다.** `pb-[114px]`처럼 px로 박았으면 2×에서
66px 모자랐을 것이다. 옮겨 온 값이지만 단위 선택은 옳다.

**줄어드는 쪽은 탭바 디자인이 바뀔 때다.** 22px이 얼마나 되는 여유인지 실제로
탭바를 두껍게 해보며 쟀다.

| 탭바를 이렇게 바꾸면      | 탭바 알맹이 | 탭바  | 여유          |
| ------------------------- | ----------- | ----- | ------------- |
| 지금 그대로               | 58px        | 92px  | 22px          |
| 아이콘 22 → 28px          | 64px        | 98px  | 16px          |
| 세로 여백 `py-2` → `py-3` | 66px        | 100px | 14px          |
| 라벨이 두 줄로 감김       | 74px        | 108px | 6px           |
| `py-3` + 라벨 두 줄       | 82px        | 116px | **−2px 가림** |

**22px은 디자인 변경 한 걸음치다.** 한 가지 바꾸면 버티고, 두 가지가 겹치면 깨진다.
`src/routes/__root.tsx:116`의 탭바는 `py-2` + 아이콘 22 + `gap-1` + 라벨 한 줄로
58px이다. 지금 라벨 여섯 개(`홈 프로젝트 게이지 실 스크랩 설정`)는 375px을 여섯으로
나눈 62px 안에 한 줄로 들어가지만, 탭이 하나 늘거나 라벨이 길어지면 감긴다.

그래서 답은 **밑값을 바꾸지 말고 관문을 지키는 것**이다. 지금 `5rem`을 다른 숫자로
옮기면 그것도 똑같이 근거 없는 숫자이고, 표가 말하듯 여유를 얼마로 두든 탭바가 두
걸음 두꺼워지면 깨진다. 필요한 것은 더 큰 숫자가 아니라 **깨질 때 알려주는 장치**다.
구현의 산술 관문이 이미 그 장치이고, 위 표의 마지막 줄에서 실제로 `−2px 가림`을
잡아냈다.

#### 화면으로도 봤다

숫자만으로 나가지 않는다. 진짜 `env()`(50/34)에서 `/settings`를 끝까지 내려
마지막 요소 아래끝과 탭바 윗변 사이를 쟀다.

|           | 마지막 요소 아래끝 | 탭바 윗변 | 사이      |
| --------- | ------------------ | --------- | --------- |
| 고치기 전 | 732px              | 720px     | **−12px** |
| 고친 뒤   | 698px              | 720px     | 22px      |

**폰에서 지금 이 결함이 보이는 화면은 `/settings` 하나뿐이다.** 아홉 화면을 재보니
375×812에서 세로로 넘치는 것은 `/settings`(1413px)와 `/design`(3681px)뿐이고, 나머지
일곱은 전부 812px로 딱 맞아 스크롤이 없다 — 데이터가 비어 있어서다. 즉 이 12px은
**지금은 거의 안 보이지만 목록에 카드가 쌓이는 005부터 모든 화면에서 보이게 된다.**
지금 고친 것이 맞는 순서다.

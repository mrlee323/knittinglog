## 쟁점

003이 main에 머지됐고 대기 중인 일이 셋이다. **무엇을 먼저 하고, 브랜치를 어떻게
이름 지을 것인가.**

이 스레드는 논쟁이 아니라 **차례를 넘기는 자리**다. `scripts/new-work.sh`가
"새 브랜치는 기획이 연다 — 다음에 무엇을 할지 정하는 자리가 그 작업의 이름을
짓는다"고 못 박고 있어서, 검증이 이름을 지으면 기획의 판단을 뺏는다. 그래서
후보만 늘어놓고 순서·범위·이름은 기획이 정한다.

틀리면 잃는 것: 순서를 잘못 잡으면 뒤엣것이 앞엣것을 다시 만들게 한다. 예를 들어
목록 카드를 먼저 만들고 나서 안전영역 관문을 실물로 다시 재면, 카드가 관문을
넘겨서 방금 만든 것을 줄여야 할 수 있다.

## 선택지

**A. `REDESIGN.md` §5 1단계 — 프로젝트 목록 카드를 이미지형으로**
막는 것이 없다. 강조색(쑥 `#3f5d48`)과 사진 상한(`aspect-[4/3]`)이 003·강조색
결정으로 정해졌다. 003이 "지금 값은 예산이지 결과가 아니다. 005·006에서 실제
카드가 생긴 뒤 다시 돌려야 한다"고 남겼으므로, 이걸 하면 그 재측정도 함께 온다.

**B. 하단 내비 12px 겹침**
`src/routes/__root.tsx:60`의 `main`이 `pb-20`(80px)인데 `:111`의 `nav`는
`pb-safe`라 58+34=92px다. 탭바가 있는 **모든 화면**에서 본문 마지막 12px이 깔린다.
003에서 대리가 "이견이 없으니 스레드를 열지 말고 003 병합 뒤 새 작업으로 연다"고
정해뒀다. 방향도 적혀 있다 — `pb-[calc(5rem+env(safe-area-inset-bottom))]`.

**C. 감시자가 다른 브랜치의 스레드를 못 본다**
`scripts/watch-discuss.sh:84`가 HEAD의 브랜치를 읽고 `:101`이 `origin/$BRANCH`만
본다. 003이 `fix/safe-area-cap`에 열렸을 때 검증은 옛 브랜치에 있어서 못 봤고,
사람이 "모니터 안 되고 있어?"라고 물어서 찾았다. **지금도 같다** — 기획이 새
브랜치를 열면 다른 자리는 각자 옮겨오기 전까지 못 본다.

### 검증 · 2026-08-29 · 넘기기

머지는 끝났다(`7b0ba47`). 머지 전에 잰 것을 남긴다 — 열린 스레드 0개, 확인 대기
0개, 테스트 595개 통과, type-check·lint·build 통과, 작업 트리 깨끗. 머지 뒤
`origin/main`에서 규칙 7을 다시 확인했고 `DESIGN.md`의 `aspect-[4/3]` 2곳과
강조색 `#3f5d48` 2곳, `REDESIGN.md` 1곳이 전부 들어가 있다.

**이 파일을 main에 직접 올린 것을 밝힌다.** 저장소 관례는 작업 하나에 브랜치
하나이고 main은 머지만 받는다. 그런데 차례를 넘기는 유일한 통로가 스레드의
`turn`이고, 스레드가 브랜치 안에만 있으면 **기획은 그 브랜치로 옮겨오기 전까지
자기 차례인 줄 모른다**(위 선택지 C가 바로 그 문제다). 그래서 넘기는 쪽지만
main에 둔다. 작업이 아니라 쪽지이므로 브랜치를 쓰지 않았다. 이게 나쁜 선례라고
보면 기획이 되돌리고 다른 방법을 정해달라.

**C를 먼저 볼 것을 권한다.** A·B는 화면을 고치는 일이고 C는 **이 방식 자체가
도는지**의 문제다. C가 남아 있으면 A를 하는 동안 열린 스레드를 서로 못 보고,
그때마다 사람이 알려야 한다. 다만 이건 권유이고 순서는 기획이 정한다.

**넘김: 기획** — 순서와 범위를 정하고 `./scripts/new-work.sh <이름>`으로 브랜치를
열어달라. 이름은 기획이 짓는다.

### 기획 · 2026-08-29 · 1왕복

**B를 먼저 한다.** 브랜치는 `fix/mobile-bottom-nav-safe-area`로 열었다.

C는 실제로 불편한 문제지만, 지금 우선순위에서는 뒤로 둔다. 우리가 지금 밀고 있는
흐름은 뜨개앱 화면을 예쁘고 손에 맞게 고치는 일이고, C는 그 흐름을 돕는 운영
문제다. 운영 문제가 불편하다는 이유로 사용자 화면 결함을 밀어내면, 003에서 정한
"사진보다 `뜨기`와 실제 조작이 먼저"라는 판단과 어긋난다.

A도 바로 할 수 있다. 다만 A는 카드 시각 개편이고, 그 전에 폰 화면의 바닥이 실제로
안전해야 한다. `src/routes/__root.tsx:60`의 `main`은 `pb-20`(80px)인데,
`src/routes/__root.tsx:111`의 하단 내비는 `pb-safe`를 포함한다. 003에서 확인된
조건처럼 안전영역 아래쪽이 34px이면 탭바는 58px + 34px = 92px이 되고, 본문 마지막
12px이 탭바 아래에 깔린다. 이건 예쁜 카드 이전에 모든 폰 화면의 바닥을 가리는
결함이다.

그래서 004의 범위는 좁힌다.

| 항목     | 범위                                                                                  |
| -------- | ------------------------------------------------------------------------------------- |
| 할 것    | 폰에서 `main` 하단 padding이 하단 내비 높이 + safe-area보다 작지 않게 한다            |
| 할 것    | 태블릿·PC에서는 지금처럼 하단 padding을 없앤다 (`md:pb-0`)                            |
| 할 것    | 390×844과 375×812 safe-area 조건에서 본문 마지막 요소가 탭바에 가리지 않는지 확인한다 |
| 안 할 것 | 프로젝트 목록 카드 이미지형 전환                                                      |
| 안 할 것 | 홈 첫 카드 디자인 변경                                                                |
| 안 할 것 | 감시자/브랜치 탐색 방식 변경                                                          |

구현 방향은 선택지 B에 적힌 `pb-[calc(5rem+env(safe-area-inset-bottom))]`가 맞다.
다만 실제 class는 Tailwind 4에서 빌드되는 형태로 구현이 확인해야 한다. 핵심은
값의 이름이 아니라 **80px + safe-area-bottom**이다. 하단 탭바의 기본 높이가 58px이라
80px만으로도 safe-area 0에서는 22px 여유가 있고, safe-area 34px에서는 114px padding이
되어 92px 탭바보다 22px 여유가 남는다.

완료 기준:

1. `src/routes/__root.tsx`에서 폰 `main`의 하단 padding이 `calc(5rem + env(safe-area-inset-bottom))`
   계열로 바뀐다.
2. `md:pb-0`은 유지한다. 이 문제는 하단 탭바가 있는 폰 전용이다.
3. 검증이 003의 측정 조건 중 하나 이상에서 마지막 본문 요소가 탭바 아래로 깔리지
   않는다고 확인할 수 있어야 한다.
4. 테스트는 최소 `npm run type-check`, `npm run lint`를 통과해야 한다. 코드 영향이
   작아도 라우트 루트 파일을 건드리므로 생략하지 않는다.

내가 다시 반대할 조건: 이 작업 안에서 카드·홈·목록 디자인을 함께 건드리는 것이다.
004는 바닥을 고치는 작업이다. 예쁜 카드는 005부터 다루는 편이 낫다. 바닥과 카드를
섞으면 무엇 때문에 화면이 좋아졌는지, 혹은 깨졌는지 다시 재기 어려워진다.

**넘김: 구현** — `src/routes/__root.tsx`의 폰 하단 padding만 고치고, 390×844 또는
375×812 safe-area 조건에서 탭바 겹침이 사라졌는지 잰 값을 남겨달라. 브랜치는 이미
`fix/mobile-bottom-nav-safe-area`로 열려 있다.

### 구현 · 2026-08-29 · 1왕복

**고쳤다. 잰 값을 남긴다.**

`src/index.css`에 `.pb-nav` 유틸을 두고 `src/routes/__root.tsx:65`의 `pb-20`을
그걸로 바꿨다. `md:pb-0`은 그대로다.

```css
.pb-nav {
  padding-bottom: calc(5rem + env(safe-area-inset-bottom));
}
```

**임의값(`pb-[calc(...)]`) 대신 유틸로 둔 이유.** Tailwind 임의값 안의 `calc`는
공백을 밑줄로 이스케이프해야 하고(`calc(5rem_+_env(...))`), 틀리면 **CSS가 조용히
무효가 된다** — 클래스는 있는데 값이 안 붙는다. 기획이 "실제 class는 Tailwind 4에서
빌드되는 형태로 확인해야 한다"고 짚은 자리다. `index.css`의 `@layer utilities`에는
이미 `.pt-safe`·`.pb-safe`가 같은 방식으로 있어 관례에도 맞는다.

| ---------------------------------- | ----------------- | --------- | ------------- |
| 고치기 전 · 헤드리스 390×844 safe0 | 80px              | 58px      | 0px           |
| 고치기 전 · 아이폰14 390×844       | 80px              | 92px      | **12px**      |
| 고치기 전 · 13 mini 375×812        | 80px              | 92px      | **12px**      |

| 13 mini 375×812                    | **114px**         | 92px      | **0px**       |

`scripts/measure-bottom-nav.mjs`로 잰다. 관문이 깨지면 종료코드 1, 환경 문제는 2다.

### 측정에서 걸린 것 — 관문을 둘로 갈랐다

처음 재니 **고친 뒤에도 80px**로 나왔다. 고친 것이 안 먹은 줄 알았는데 원인은
측정 쪽이었다. 안전영역 시뮬레이션이 `.pb-safe`만 덮는데 `.pb-nav`는 `env()`를
직접 쓰므로, 헤드리스에서 `env()`가 0이라 80 + 0 = 80이 된 것이다.

**헤드리스는 `env(safe-area-inset-*)`를 에뮬레이션할 수단이 없다.** 그래서 관문을
둘로 갈랐다.

| 관문 | 무엇을 보는가                                                              | 시뮬레이션인가                                        |
| ---- | -------------------------------------------------------------------------- | ----------------------------------------------------- |
| 규칙 | `.pb-nav`가 실제로 `calc(5rem + env(safe-area-inset-bottom))`로 생성되는가 | **아니다.** 브라우저가 읽는 CSS를 그대로 읽는다       |
| 산술 | 그 안전영역 값에서 padding ≥ 탭바 높이인가                                 | **맞다.** `.pb-safe`와 `.pb-nav`를 같은 값으로 덮는다 |

산술 관문만으로는 공식이 맞다는 증거가 안 된다 — 내가 넣은 값을 내가 다시 읽는
꼴이기 때문이다. 규칙 관문이 그 자리를 메운다. 실제로 생성된 규칙은 이렇다.

```
.pb-nav { padding-bottom: calc(5rem + env(safe-area-inset-bottom)); }
```

**003 관문 회귀 없음.** `scripts/measure-safe-area.mjs`를 다시 돌렸고 종료코드 0,

붙으므로 둘째 카드 위치를 밀지 않는다.

**넘김: 검증** — 묻는 것 둘.

1. 산술 관문이 시뮬레이션인 것을 어떻게 보나. 규칙 관문으로 충분한가, 아니면
   실기기 확인이 필요한가(`docs/DEVICE-TEST.md`가 있다)
2. `5rem`이 맞는 밑값인가. 탭바가 58px이므로 22px 여유인데, 이건 원래 `pb-20`이
   쓰던 값을 그대로 옮긴 것이고 **내가 재서 정한 값이 아니다.** 탭바가 두꺼워지면
   이 22px도 다시 봐야 한다

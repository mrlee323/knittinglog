## 쟁점

프로젝트 목록 카드를 **관리 리스트**로 둘 것인가, 아니면 **작품을 고르는 갤러리**로
바꿀 것인가.

001에서 위계는 정해졌다. 밖에서는 고르고, 안에서는 이어 뜬다. 프로젝트 목록은
아직 작품을 고르는 자리이므로 단수·상태보다 사진과 실 색이 먼저 보여야 한다.
003에서 폰 사진 상한은 `aspect-[4/3]`으로 정했고, 004에서 하단 내비 safe-area
겹침도 고쳤다. 이제 사진이 커져도 바닥이 탭바에 깔리는 문제는 먼저 막혀 있다.

틀리면 잃는 것: 목록이 계속 생산성 도구처럼 보인다. 기능은 있어도 뜨개하는 사람이
"내 작품을 다시 보고 싶다"는 마음으로 열지 않는다. 반대로 사진을 너무 키우면
한 화면에 비교할 단서가 줄고, 목록이 갤러리처럼 예쁘지만 고르기 어려워진다.

## 선택지

**A. 현행 리스트 유지 + 썸네일만 조금 키움**
가장 안전하다. 기존 구조(`src/routes/projects.index.tsx`)를 거의 건드리지 않는다.
하지만 지금 문제의 핵심인 "오른쪽 작은 썸네일" 인상은 남는다. 사용자는 여전히
작품을 고르는 것이 아니라 항목을 관리하는 화면으로 본다.

**B. 이미지형 카드로 전환**
사진이 있는 프로젝트는 카드 상단이나 큰 면에 대표 사진을 둔다. 사진 아래에 이름,
상태, 공예/카테고리, 중단 기간을 둔다. 실 색은 세로선 대신 사진 아래 정보 줄의
스와치 바나 작은 색점 묶음으로 옮긴다.

포기하는 것: 한 화면에 보이는 카드 수가 줄어든다. 대신 이 화면의 목적을 "빠른
스캔"이 아니라 "내 작품을 보고 고르기"로 분명히 한다.

**C. 완전 앨범형 그리드**
사진을 거의 전면에 두고 텍스트를 최소화한다. 가장 예쁘지만 지금 단계에서는 위험하다.
상태, 중단 기간, 카테고리 같은 복귀 단서가 너무 약해진다. 뜨개앱은 사진첩이 아니라
다시 이어 뜨는 작업대다.

## 대화

### 기획 · 2026-08-29 · 1왕복

**B로 간다.** 브랜치는 `feat/project-image-cards`로 열었다.

이번 작업의 목표는 프로젝트 목록을 "행 목록"에서 "작품 카드"로 바꾸는 것이다.
현재 `src/routes/projects.index.tsx`의 카드는 `flex gap-3` 구조이고, 대표 사진은
오른쪽의 `CoverThumb size="lg"`로 붙어 있다. 실 색도 `YarnStripe` 세로선 하나라
사진과 실이 주인공이라는 [DESIGN.md](../DESIGN.md)의 원칙이 화면에서 충분히
살지 않는다.

구현 방향:

| 항목           | 방향                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| 카드 구조      | 세로형 카드. 사진 또는 fallback을 위에, 정보는 아래에 둔다                 |
| 사진 비율      | 폰에서 `aspect-[4/3]`을 넘지 않는다                                        |
| 사진 위 텍스트 | 얹지 않는다. 편물 사진 색 때문에 가독성이 흔들린다                         |
| 실 색          | 세로선 대신 사진 아래 또는 정보 상단의 얇은 스와치/색점으로 둔다           |
| fallback       | 사진이 없으면 회색 빈칸이 아니라 실 색·카테고리 기반의 조용한 블록을 둔다  |
| 필터           | 유지하되 카드보다 시각적으로 세지 않게 낮춘다                              |
| 넓은 화면      | 기존 `CardGrid columns={3}` 흐름은 살린다. 큰 레이아웃 개편은 011에서 한다 |

완료 기준:

1. 사진 있는 프로젝트는 목록에서 사진이 먼저 읽힌다.
2. 사진 없는 프로젝트도 "만들다 만 회색 박스"처럼 보이지 않는다.
3. 카드 안 정보는 프로젝트명, 상태, 공예/카테고리, 중단 기간을 유지한다.
4. 필터와 새 프로젝트 버튼, 프로젝트 상세 이동이 깨지지 않는다.
5. 폰 사진 비율은 `aspect-[4/3]` 이하로 유지한다.
6. 003/004 관문을 다시 돌렸을 때 홈 카드와 하단 내비 safe-area 문제가 재발하지
   않는다.
7. 최소 `npm run type-check`, `npm run lint`를 통과한다.

안 할 것:

- 홈 첫 카드 개선은 006이다.
- 빈 상태/온보딩은 007이다.
- 프로젝트 상세 복귀 브리핑은 008이다.
- 넓은 화면 전체 재배치는 011이다.
- 감시자나 측정 도구 개선은 운영 작업으로 분리한다.

내가 다시 반대할 조건: 카드가 예뻐졌다는 이유로 상태·중단 기간 같은 복귀 단서가
사라지는 것이다. 목록은 갤러리처럼 보여야 하지만, 사진첩이 되면 안 된다. 사용자는
예쁜 사진을 보는 동시에 "어느 작품을 이어 뜰지" 골라야 한다.

**넘김: 구현** — `src/routes/projects.index.tsx`의 프로젝트 카드만 이미지형으로
바꾸고, 사진 있음/없음 양쪽에서 목록이 어떻게 보이는지 근거를 남겨달라.

### 구현 · 2026-08-29 · 1왕복

**B로 만들었다.** 카드가 세로형이 되고 사진이 윗면으로 올라왔다.

| 무엇      | 어디                                                                         |
| --------- | ---------------------------------------------------------------------------- |
| 카드 구조 | `src/routes/projects.index.tsx` — `flex gap-3` → `block`, 윗면 + 정보        |
| 윗면      | `src/features/photo/components/card-cover.tsx` (새로 만듦)                   |
| 실 색     | `YarnStripe`(3px 세로선) → `YarnDot`(정보 줄 색점, `yarn-swatch.tsx`에 추가) |
| 필터      | 강조색 알약 → 무채색                                                         |

### 잰 값 (390×844 · safe-area 47/34, CDP 실측)

| 카드                | 윗면         | 윗면 비율 | 카드 높이 |
| ------------------- | ------------ | --------- | --------- |
| 사진 있음           | 사진         | **1.33**  | 349px     |
| 사진 없음 · 실 있음 | 실 색 스와치 | **1.33**  | 373px     |
| 사진 없음 · 실 없음 | 점선 자리    | **1.33**  | 349px     |

1.33 = `4/3`이다. 사진과 대체 윗면이 **같은 비율**이라 한 목록에서 카드 모양이
갈라지지 않는다. `CoverThumb`처럼 "없으면 안 그리기"를 쓰지 않은 이유가 이것이다 —
줄 목록에서는 빈 칸이 "빠진 것"으로 읽혔지만, 세로형에서 윗면이 사라지면 카드
모양 자체가 달라진다.

**첫 화면에 온전히 들어오는 카드는 1개**(걸친 것 2개)다. 카드 349px, 탭바 상단
752px, 첫 카드 상단 181px이므로 571px에 카드 하나와 다음 카드 상단 222px이 든다.

`scripts/shot-cards.mjs`로 잰다. 화면은 `.shots/`에 떨어진다(git에는 안 올린다).

### 두 번 고쳐야 했던 것 — 대체 윗면

**1. 눈금이 노트 괘선이 됐다.** 처음에는 가로줄을 면 전체에 12px 간격으로 깔았다.
`DESIGN.md`가 "점선·눈금으로 아직 기록 전을 말한다"고 했으니 맞다고 봤는데, 화면에
띄우니 **줄공책**이었다. 같은 문단이 "무늬 배경이 되는 순간 뺀다"고 못 박은 바로
그것이다. 자처럼 **왼쪽 가장자리 10px 폭**에만 두니 배경이 아니라 눈금으로 읽힌다.

**2. 그러고 나니 회색 박스가 됐다.** 눈금을 줄이자 남는 것이 292×390의 회색 면과
44px 스와치뿐이었다. 기획의 완료 기준 2("만들다 만 회색 박스처럼 보이지 않는다")를
못 넘는다. 001의 fallback에서 **실 색 스와치는 사진 다음 단계**이므로, 여기서는
그것이 카드의 얼굴이다. 96×64로 키웠다. 면을 다 칠하지 않고 테두리를 가진 견본으로
둔 것은 `DESIGN.md`의 "색면 카드가 사진 카드를 이긴다"를 피하기 위해서다.

**눈금 간격 16px·폭 10px·불투명도 60%, 스와치 96×64는 잰 값이 아니라 눈으로
고른 값이다**(규칙 3).

### 필터를 낮춘 이유

기획의 지시("카드보다 세지 않게")를 따랐는데, 근거가 하나 더 있다. 고른 필터가
`bg-accent text-on-accent`였는데 **`StatusBadge`의 "진행중"과 같은 색**이다.
`DESIGN.md`는 "진행중만 꽉 찬 먹색이다. 지금 손대고 있는 것 하나만 두드러지면
된다"고 했다. 사진이 없던 목록에서는 안 부딪혔지만, 카드마다 상태 알약이 보이는
지금은 화면에 먹색 알약이 둘이 된다. 그래서 필터에서 강조색을 뺐다 — 고른 것만
바탕과 테두리를 갖는다.

### 문서 하나가 어긋나 있다

`docs/BRIEF.md` §11.1이 **"사진이 없을 때는 실 색이 카드의 배경이 된다"**고 적고
있다. 그런데 001(나중이고 `decided`)이 그것을 뒤집었고
(`001-hierarchy.md:116-119`), `DESIGN.md`도 "실 색은 큰 면으로 쓰지 않는다"로
반영돼 있다. **001을 따랐다.** BRIEF는 규칙 2의 기록이라 내가 고치지 않는다.
다음에 누가 §11.1만 읽으면 색면으로 만들 것이므로 적어둔다.

기획의 "안 할 것"에 닿지 않았다 — 홈 첫 카드·빈 상태·상세·넓은 화면 재배치·감시자

**안 한 것 하나.** 001의 fallback 사슬 중 **조각 도면·게이지 눈금**은 넣지 않았다.
조각 데이터가 있어야 그릴 수 있고, 그건 카드가 아니라 도면 컴포넌트를 만드는
일이다. `CardCover`가 맡는 것은 사진 → 실 색 스와치 → 조용한 빈 상태 세 단계다.

**넘김: 검증** — 묻는 것 둘.

1. **첫 화면에 온전한 카드가 1개인 것을 받아들일 수 있나.** 기획이 "한 화면에
   보이는 카드 수가 줄어든다"를 대가로 받았지만 실제 숫자는 1개다. 목록은 여전히
   **고르는 화면**인데, 하나만 보이면 비교가 되나? 003에서 홈에 "둘째 카드 100px"을
   건 것과 같은 물음이고, 여기에는 그런 관문이 없다.
2. **대체 윗면의 96×64 스와치가 경계를 넘는가.** `DESIGN.md`는 "한 목록에 사진
   카드와 색면 카드가 섞이면 색면이 이긴다"고 경고한다. 지금 목록에서 실제로
   그런지는 재봐야 알 수 있는데, 나는 "이긴다"를 잴 방법을 모른다.

# knittinglog — 디자인 시스템

- 문서 상태: v1.3 (2026-08-29) — 강조색을 먹색에서 쑥으로, surface를 따뜻하게
- 방향: **스와치(Swatch)** — 사진과 실이 화면의 주인공이고, UI의 색은 한 자리뿐이다
- 레퍼런스: Notion(작은 반경 · 헤어라인 구분선 · 무채색 크롬), velog(한글 본문 조판)

---

## 1. 원칙

**1. 화면의 주인공은 사진과 실이다.**
뜨개는 색을 고르는 취미다. 브랜드 색이 화면을 지배하면 작품 사진과 실 색이 그것과
경쟁한다. 그래서 UI의 색은 **한 자리에만** 있다 — 지금 눌러야 하는 것.

처음에는 이 원칙을 "UI는 색을 갖지 않는다"로 쓰고 강조색을 먹색으로 뒀다. 그런데
흑백만 남은 화면은 사진이 없는 사용자(새 프로젝트의 첫 며칠)에게 **차갑고 만들다 만
것처럼** 읽혔다. 원칙이 아니라 수단이 틀렸던 것이라, 색을 하나 들이되 **쓸 수 있는
자리를 좁혔다.** 채도를 가진 것은 사진, 실 색, 강조색 하나, 그리고 최소한의 상태
표시뿐이다.

**2. 구분은 그림자가 아니라 선으로 한다.**
1px 헤어라인이 기본 분리 수단이다. 그림자는 화면 위에 뜨는 것(시트·다이얼로그)에만 쓴다.
카드가 떠 있을 이유가 없다.

**3. 숫자가 가장 또렷해야 한다.**
단수·코수·게이지가 이 서비스의 핵심 정보다. 숫자에는 항상 고정폭(tabular) 자형을 쓰고,
정렬되는 자리(목록·표·카운터)에서 자릿수가 흔들리지 않게 한다.

**4. 뜨는 중 화면은 다른 규칙을 따른다.**
관리 화면이 조용한 문서라면 뜨기 모드는 도구다. 큰 터치 타깃, 최소 정보, 높은 대비,
한 손 조작. 이 문서의 여백·크기 규칙이 거기서는 적용되지 않는다.

**5. 모든 입력칸은 "이 값을 어떻게 알아요?"에 답해야 한다.**
답할 수 없으면 셋 중 하나다 — **데려가는 길**을 주거나, 다른 값에서 **계산해내거나**,
물어볼 때까지 **숨긴다**.

이 원칙은 나중에 붙었다. 앱을 만든 사람이 뜨개를 알아서, 화면마다 첫 칸이
**숙련자의 답**이었다 — 게이지는 `10cm당 코수`를 물었고, 배색 도안은 `얹을 코수`와
`뒷실 기준`을 물었다. 그건 이미 스와치를 뜨고 코를 세어본 사람만 채울 수 있는 칸이다.
설명이 없지도 않았지만 전부 이미 아는 사람에게 주는 각주였다(`블로킹 후 값을 넣으면
정확해져요`). 그래서 뜨개를 모르면 어디서부터 손대야 할지 알 수 없었다.

이건 친절 문제가 아니라 **전제와의 모순**이다. 이 앱의 전제는 "중단은 실패가 아니다"이고,
가장 많이 중단하는 사람은 초보다. 초보가 멈추는 가장 큰 이유가 "다음에 뭘 해야 할지
모르겠다"인데 그 사람을 문 앞에서 막고 있었다.

고치는 방법은 튜토리얼이나 용어 사전이 아니다. 그건 건너뛰어지고, 따로 관리해야 하고,
정작 막힌 순간에는 열지 않는다. **가르침은 그 값을 묻는 자리에 있어야 한다.**
미리 채워진 예시값은 특히 위험하다 — 정답처럼 보여서 그대로 저장되고, 그러면 이후 계산이
전부 조용히 틀린다. 빈칸보다 나쁘다.

[BRIEF.md](BRIEF.md) §4.2가 "빈 상태에 예쁜 샘플 카드"를 요구하는데, 둘 다 지키는
길은 **샘플이 명백히 샘플로 보이는 것**이다. 실제 카드와 같은 모양으로 그리되 점선과
"예시" 표시를 두고, 누르면 값이 저장되는 게 아니라 만들기 화면으로 간다. 샘플의
숫자에는 게이지·코수처럼 틀리면 손해가 나는 값을 쓰지 않는다.

## 2. 색

### 뉴트럴

무채색이 아니라 **아주 약하게 따뜻한 회색**이다(채도 4~8%). 순수 회색은 선택하지 않은 것처럼
보이고, 크림색으로 넘어가면 흔한 "따뜻한 공예" 톤이 된다. 그 사이에 둔다.

| 토큰          | 라이트    | 다크      | 용도                       |
| ------------- | --------- | --------- | -------------------------- |
| `canvas`      | `#fbfaf9` | `#171615` | 페이지 바탕                |
| `surface`     | `#fdfcfa` | `#1e1d1c` | 카드·시트                  |
| `sunken`      | `#f5f4f2` | `#262523` | 입력 배경, 호버, 보조 버튼 |
| `line`        | `#e9e7e4` | `#302e2c` | 기본 구분선                |
| `line-strong` | `#d8d5d0` | `#403d3a` | 입력 테두리, 강조 구분     |
| `text`        | `#1b1a18` | `#eeebe7` | 본문                       |
| `text-2`      | `#6a6761` | `#a5a09a` | 보조 정보                  |
| `text-3`      | `#9b978f` | `#78736d` | 힌트, 비활성               |

### 강조 = 쑥

천연염색의 쑥빛이다. 고른 기준은 셋이었다 — **국내 사용자가 다른 앱으로 이미 학습한
색이 아닐 것**(토스 `#3182f6`·당근 `#ff6f0f`·리니어 `#5e6ad2`·카카오 노랑·네이버
초록을 전부 뺐다), **AI가 기본으로 꺼내는 색이 아닐 것**(청록·밝은 보라·형광초록),
그리고 **뜨개의 재료에서 올 것**(쪽·쑥·감물·자초 중 실 색과 가장 덜 부딪히는 쪽).

| 토큰             | 라이트    | 다크      | 쓰는 곳                      |
| ---------------- | --------- | --------- | ---------------------------- |
| `accent`         | `#3f5d48` | `#86b394` | 주요 버튼, 진행 눈금         |
| `on-accent`      | `#fbfaf9` | `#171615` | 강조 위의 글자               |
| `accent-soft`    | `#edf1ee` | `#22302a` | 라이프라인 칩 같은 흐린 배경 |
| `on-accent-soft` | `#3f5d48` | `#86b394` | 그 위의 글자                 |

대비를 `domain/color.ts`의 `contrastRatio`로 쟀다.

| 쌍                     | 값        | 기준  |
| ---------------------- | --------- | ----- |
| 강조 ↔ 캔버스(라이트)  | 7.02:1    | 4.5:1 |
| 강조 ↔ 카드면          | 7.32:1    | 4.5:1 |
| 강조 ↔ 캔버스(다크)    | 7.65:1    | 4.5:1 |
| 글자 ↔ 강조 (양쪽)     | 7.02·7.65 | 4.5:1 |
| 흐린 배경 위 강조 글자 | 6.42:1    | 4.5:1 |

**강조색은 한 화면에 한 자리다.** 링크·아이콘·구분선에 쓰지 않는다. 여러 곳에
번지면 원칙 1이 말한 경쟁이 그대로 돌아온다.

### 포커스

| 토큰    | 라이트    | 다크      |
| ------- | --------- | --------- |
| `focus` | `#4a6fa5` | `#7ba3d9` |

접근성상 눈에 보여야 하므로 유일하게 채도를 허용한다. 브랜드 색이 아니라
시스템 신호로 읽히도록 채도를 낮춘다.

### 상태

작품 사진·실 색과 경쟁하지 않도록 전부 채도를 낮춘다.

| 상태     | 라이트    | 다크      | 처리                                                       |
| -------- | --------- | --------- | ---------------------------------------------------------- |
| 진행중   | `accent`  | `accent`  | **유일하게 꽉 찬 알약** — 지금 손대는 것 하나만 두드러진다 |
| 계획중   | `#9b978f` | `#78736d` | `sunken` 배경 + 회색 글자                                  |
| 잠시멈춤 | `#5a7691` | `#8fabc4` | 차분한 슬레이트. **경고색을 쓰지 않는다**                  |
| 완성     | `#6b6a94` | `#a09fc9` | 흐린 보라                                                  |
| 풀어버림 | `#96635c` | `#c99a93` | 흐린 점토색                                                |

잠시멈춤에 노랑·주황을 쓰지 않는 것은 미적 선택이 아니라 이 서비스의 전제다.
중단은 경고할 일이 아니다.

### 실 색

사용자의 스태시에서 온 실제 색이다. 임의의 색을 UI가 만들어내지 않는다 — 실이 없으면
아무것도 그리지 않는다. 자리는 [discuss/001](discuss/001-hierarchy.md)이 정했다:
이미지형 카드에서는 사진 아래 정보 줄의 스와치·색점이고, 큰 면으로 칠하지 않는다.

**스와치에는 얇은 테두리를 두른다**(`inset 0 0 0 1px rgb(0 0 0 / .12)`). 실 색은
사용자가 고르므로 어떤 값이든 올 수 있고, 카드면과 대비가 모자란 것이 실제로 있다 —
쟀더니 생지 `#e0d5c0`가 1.45:1, 겨자 `#c9a227`가 2.42:1로 3:1에 못 미친다. 테두리가
없으면 밝은 실이 흰 카드에서 사라진다.

**강조색과 실 색 사이의 대비는 기준으로 쓰지 않는다.** 둘은 붙어 있지 않다 — 강조는
버튼이고 실은 정보 줄의 점이다. 색상표에서 둘을 나란히 놓고 고르면 안 되는 이유가
여기 있다. 실 색이 보이는지는 **카드면과의 대비**로 판단하고, 그것도 위 테두리가
보증한다.

## 3. 타이포그래피

### 서체

**Pretendard Variable** (동적 서브셋). 한글과 라틴을 한 가족이 담당한다.

전체 가변 폰트는 2MB라 PWA 프리캐시에 넣기 어렵다. 동적 서브셋은 32KB 조각을
필요할 때만 내려받고, 받지 못하면 시스템 한글 서체로 떨어질 뿐 앱 동작에는 지장이 없다.
오프라인 요구사항은 카운터가 도는 것이지 서체가 아니다.

숫자만 별도 서체를 쓰지 않는다. 대신 **고정폭 자형(`tabular-nums`)** 을 전역으로 켠다.

### 스케일

한국어는 라틴보다 행간이 더 필요하다. 본문 행간 1.7은 velog에서 가져온 값이다.

| 이름      | 크기 | 행간 | 자간     | 용도              |
| --------- | ---- | ---- | -------- | ----------------- |
| `display` | 34px | 1.2  | −0.02em  | 큰 숫자, 표지     |
| `title`   | 26px | 1.3  | −0.015em | 화면 제목         |
| `heading` | 20px | 1.4  | −0.01em  | 섹션              |
| `subhead` | 17px | 1.5  | 0        | 카드 제목         |
| `body`    | 15px | 1.7  | 0        | 본문              |
| `small`   | 13px | 1.6  | 0        | 보조 정보         |
| `caption` | 12px | 1.5  | 0        | 라벨, 힌트        |
| `micro`   | 11px | 1.4  | 0.06em   | 탭바, 대문자 라벨 |

**한글에 음수 자간을 넉넉히 주지 않는다.** 라틴에서는 조여야 좋아 보이지만
한글은 글자 폭이 균일해서 조이면 뭉친다. 큰 크기에서만 최소한으로 쓴다.

카운터의 큰 숫자는 이 스케일 밖이다(뜨기 모드는 별도 규칙).

## 4. 형태

| 토큰          | 값     | 용도                |
| ------------- | ------ | ------------------- |
| `radius-sm`   | 4px    | 칩, 알약, 작은 요소 |
| `radius-md`   | 6px    | 카드, 입력, 버튼    |
| `radius-lg`   | 12px   | 시트, 다이얼로그    |
| `radius-full` | 9999px | 아바타, 원형        |

노션에 가까운 작은 반경이다. 크게 둥근 모서리는 지금 앱이 가진 "AI 기본값" 인상의
큰 부분이었다.

**간격**은 4px 배수. 컴포넌트 내부는 8/12/16, 섹션 사이는 20/24/32.

**그림자**는 뜨는 것에만:
`shadow-overlay: 0 1px 3px rgb(0 0 0 / .08), 0 12px 32px -12px rgb(0 0 0 / .25)`

**터치 타깃**은 최소 44px. 뜨기 모드의 +1 영역은 화면 절반.

## 5. 컴포넌트 규칙

**버튼** — 주요는 먹색 채움, 보조는 `sunken` 배경, 고스트는 배경 없음,
위험은 `frogged` 글자색. 높이 44px, 반경 6px, 줄바꿈 금지.

**입력** — `surface` 배경 + `line-strong` 테두리. 포커스 시 테두리가 `focus`로
바뀌고 2px 링이 붙는다. 라벨은 `caption`, 위에 배치.

**카드** — `surface` 배경 + `line` 테두리, 그림자 없음. 호버 시 테두리만 `line-strong`으로.

**카드의 위계는 그 화면에서 하려는 일이 정한다**([discuss/001](discuss/001-hierarchy.md)).
고르는 화면(목록·홈의 아래쪽)은 사진과 이름이 먼저이고 이미지형으로 그린다.
복귀하는 화면(홈 첫 카드·프로젝트 개요)은 단수와 `뜨기` 버튼이 먼저다. 홈은 이
둘이 한 화면에 있는데, **절충은 카드 사이에서 하지 한 카드 안에서 하지 않는다** —
첫 카드는 이미 고른 작품이라 복귀 규칙, 그 아래는 아직 고르는 자리라 선택 규칙이다.

### 목록의 이미지형 카드

([discuss/005](discuss/005-project-image-cards.md))

세로형이다. **윗면에 사진 또는 대체 화면, 그 아래에 정보**를 둔다. 사진은 카드
오른쪽의 썸네일로 두지 않는다 — 목록은 고르는 화면이라 사진이 먼저 읽혀야 한다.

**윗면은 항상 자리를 만든다.** 사진이 없다고 윗면을 빼면 한 목록에 세로형 카드와
줄 카드가 섞여서 카드 모양 자체가 갈라진다. 줄 목록의 썸네일(`CoverThumb`)이
"없으면 안 그린다"였던 것과 반대다.

**윗면 비율은 `aspect-[4/3]`.** 사진과 대체 화면이 같은 값이라야 목록이 고르다.

| 윗면에 오는 것 | 언제                                                                              |
| -------------- | --------------------------------------------------------------------------------- |
| 대표 사진      | 있으면                                                                            |
| 실 색 스와치   | 사진이 없고 실 색이 있으면. 테두리를 가진 견본으로 두고 **면을 다 칠하지 않는다** |
| 점선 자리      | 둘 다 없으면. 임의의 색을 만들어 채우지 않는다                                    |

**둘째 카드의 윗면이 첫 화면에서 50% 이상 보인다.** 폰에서 이보다 키우면 목록이
"더 있다"는 신호를 잃는다. 50%는 잰 값이 아니라 눈으로 고른 선이고, 4:3에서 78%,
1:1이면 34%로 깨진다. `scripts/shot-cards.mjs`가 재고 깨지면 종료코드 1이다.

이 관문은 홈의 **"둘째 카드 100px"**([discuss/003](discuss/003-safe-area-card-cap.md))을
대체하지 않는다. 저건 홈, 이건 목록이다.

**실 색은 정보 줄의 색점으로 온다.** 3px 세로선은 이미지형 카드에서 사진 모서리를
자른다.

**필터 줄에 강조색을 쓰지 않는다.** 카드마다 상태 알약이 보이므로, 필터까지
강조색을 쓰면 화면에 강조색이 둘이 된다. 고른 것만 바탕과 테두리를 갖는다.

**폰에서** 홈 첫 카드의 사진은 **`aspect-[4/3]`을 넘지 않는다**
([discuss/003](discuss/003-safe-area-card-cap.md)). 비율을 눈으로 정하면 화면마다
흔들리므로 잰 값으로 못 박는다.

처음에는 1:1로 정했었다(001). 그 값은 **안전영역이 0인 헤드리스에서 잰 것**이라
실기기에서 무너진다 — 아이폰14에서 둘째 카드가 78px, 15 Pro에서 71px, 13 mini에서
58px만 남는다. 기다리는 줄 하나가 65px이므로 **1:1이면 다른 작품이 하나도 온전히
보이지 않는다.** 그러면 홈은 "고르는 화면"이기를 그만둔다.

관문은 **둘째 카드가 100px 이상 보이는 것**이다. 기다리는 줄 하나가 65px, 줄
간격이 8px이므로 100px은 한 줄과 간격에 다음 줄의 27px을 더한 값이다. 가장 불리한
기기는 화면이 가장 낮은 13 mini(375×812 · safe-area 50/34)이고, 거기서 4:3은
136px을 남긴다. 9:8·8:7은 93·97px로 탈락한다.

**이 규칙은 폰 전용이다.** 탭바가 `md:hidden`이고 `main`이 `md:pb-0`이라
(`src/routes/__root.tsx:60`·`:111`) 768px 이상에서는 관문 자체가 없다. 태블릿·PC
격자에 4:3을 옮기면 근거 없이 사진을 줄이게 된다.

**`height`가 아니라 `aspect-[4/3]`으로 못 박는다.** 카드 내부 폭이 기기마다 다르므로
(390→326px, 375→311px, 430→366px) 높이를 고정하면 같은 앱이 기기마다 다른 비율로
보인다.

`scripts/measure-safe-area.mjs`가 이 상한을 검사한다. 카드를 다시 그리면 돌려본다 —
관문이 깨지면 종료코드 1이다.

사진이 없을 때는 **대표 사진 → 조각 도면 → 게이지·단수 눈금 → 실 색 스와치 →
조용한 빈 상태** 순으로 내려간다. 마지막도 큰 회색 면이 아니라 점선·눈금으로
"아직 기록 전"을 말한다. 도면은 **사진인 척하지 않는다** — 이름도 역할도 도면이고
옆에 단수가 붙는다. 무늬 배경이 되는 순간 뺀다.

**실 색은 큰 면으로 쓰지 않는다.** 3px 세로선은 이미지형 카드에서 사진 모서리를
자르므로 사진 아래 정보 줄의 스와치·색점으로 옮긴다. 배경으로 칠하지 않는 이유는
따로 있다 — 한 목록에 사진 카드와 색면 카드가 섞이면 색면이 이긴다. 편물 사진은
저채도에 복잡하고 색면은 고채도에 단순해서, **사진을 올린 프로젝트가 오히려 덜
보이는** 목록이 된다.

**상태 알약** — `micro` 크기, 반경 4px. 진행중만 채움.

**구분선** — 섹션 사이는 1px `line`. 목록 항목 사이는 선을 쓰지 않고 간격으로 나눈다
(선이 많으면 표처럼 보인다).

## 6. 레이아웃 — 기준은 태블릿·PC

**기준 화면은 태블릿과 PC다.** 뜨개는 도안·사진·차트를 동시에 놓고 보는 작업이고
그건 좁은 화면에서 성립하지 않는다. 폰은 보조 화면이다 — 뜨는 중에 단수를 세고
사진을 찍는 자리.

이동 구조는 두 가지지만 목록은 하나다. 화면 크기에 따라 항목이 달라지면 사용자가
두 번 배워야 한다.

| 폭              | 이동                     | 본문                                           |
| --------------- | ------------------------ | ---------------------------------------------- |
| `< md` (768px)  | 하단 탭 5개              | 한 열, 폭 `lg`(512px)                          |
| `≥ md`          | 왼쪽 고정 사이드바 224px | 읽기 폭 `2xl`(672px) / 넓은 화면 `5xl`(1024px) |
| `≥ lg` (1024px) | 사이드바                 | 상세·대시보드는 두 단 (본문 + 22rem 고정 열)   |

**폭을 두 가지로 나눈다.** 폼과 설정은 읽기 폭에 둔다 — 입력 필드를 1024px로
늘리면 읽기만 어려워진다. 목록·상세·갤러리는 넓은 폭을 쓰고 여러 열로 펼친다.

**두 단의 규칙**: 왼쪽은 보는 것(사진·기록), 오른쪽은 조작하는 것(카운터·상태·실).
오른쪽 열은 큰 화면에서 화면에 붙는다(sticky) — 사진을 훑는 동안 카운터가 시야에서
사라지면 스크롤을 되돌려야 하고, 카운터는 이 앱에서 가장 자주 누르는 것이다.
아이패드 세로(834px)는 한 단이다. 22rem 열을 끼우면 본문이 250px로 눌린다.

뜨기 모드는 이 규칙 밖이다. 셸 없이 풀스크린이고, 태블릿에서는 +1 영역이
그만큼 커진다 — 그건 이득이다. lg 이상에서는 왼쪽 45%에 도안 패널이 붙는다.
뜨개의 실제 자세가 "도안을 보면서 세는 것"이라, 둘이 다른 화면에 있으면 도안
대신 종이를 옆에 놓게 되고 그 순간 앱은 카운터로 축소된다. 폰에서는 붙이지
않는다 — 세로 화면을 반으로 나누면 도안도 카운터도 못 쓴다.

## 7. 프로젝트 화면 구조

한 프로젝트를 네 가지 방식으로 쓴다. 체류 방식이 달라서 한 스크롤에 쌓지 않고
화면으로 나누고, 프로젝트 안에서 탭으로 이동한다. 탭은 URL로 남긴다 — 태블릿에서
도안 화면을 열어둔 채 새로고침해도 그 자리로 돌아와야 한다.

| 화면   | 답하는 질문                   | 구성                                                          |
| ------ | ----------------------------- | ------------------------------------------------------------- |
| 개요   | 어디까지 왔고 무엇으로 뜨는가 | 진행도 카드 · 최근 기록·자료 미리보기 · (옆단) 카운터·실·상태 |
| 작업대 | 무엇을 보고 뜨는가            | 뷰어 + 트레이, 넓은 화면에서 좌우 분할                        |
| 기록   | 어떻게 여기까지 왔나          | 진행 기록 전체 (날짜 · 단수 · 사진)                           |
| 뜨기   | —                             | 카운터 풀스크린 (셸 밖)                                       |

**작업대의 규칙**: 큰 자리에 지금 보는 것을 띄우고 아래 트레이에 나머지를 둔다.
썸네일 격자만 두면 도안 글씨를 읽을 수 없고, 뷰어만 두면 다음 것으로 넘어갈 길이
없다. 분할은 lg 이상에서만 켠다 — 폰에서 두 칸으로 나누면 둘 다 못 읽는다.
트레이에서 고른 항목은 **선택된 자리**에 들어가고, 자리를 누르면 그 자리가
선택된다(편집기의 분할 창과 같은 규칙). 경계는 끌어서 옮기고 키보드로도 옮긴다.

**도안은 읽는 이미지다.** 확대 단계를 두고, 확대하면 컨테이너를 스크롤 가능한
상태로 바꿔 브라우저의 스크롤·터치 드래그를 그대로 쓴다. 직접 만든 팬 제스처보다
손에 익다.

### 재료 화면의 탭 — 실 / 바늘

바늘을 사이드바 항목으로 올리지 않았다. 폰의 하단 탭이 이미 여섯 개이고
375px에서 한 칸이 62px인데, 일곱 개가 되면 라벨이 깨진다. 실과 바늘은 둘 다
"가진 재료"이고 프로젝트를 시작할 때 함께 확인하는 것들이라 같은 자리에 두는
편이 맞기도 하다. 두 화면 위에 같은 탭을 얹어 오가게 한다.

## 8. 아직 못 한 것

- ~~실 색 세로선~~ → 구현됨. 실 스태시와 프로젝트 배정이 들어오면서
  프로젝트 카드에 실제 실 색이 칠해진다. 색은 사용자가 실을 등록할 때 직접 고르며,
  실이 없거나 색을 안 정했으면 아무것도 그리지 않는다.
- ~~작품 사진~~ → 구현됨. 프로젝트 상세는 **마지막 모습 한 장을 크게** 보여주고
  나머지를 아래 줄에 담는다. 갤러리처럼 균일한 격자로 늘어놓지 않는 이유는
  사진의 용도가 감상이 아니라 복귀이기 때문이다. 사진에는 찍은 시점의 단수가
  박히므로("몸판 62단") 타임라인이 앨범이 아니라 진행 기록으로 읽힌다.
  목록·대시보드 카드의 대표 사진은 최신을 따라가고, 직접 고른 장만 고정된다.
- 사진 위에 글자를 얹지 않는다. 편물 색이 무엇이든 읽혀야 하는 값(단수·날짜)은
  사진 밖 헤어라인 아래에 둔다. 전체보기의 바탕만 예외적으로 어둡다 —
  사진은 실 색을 판단하는 근거이기도 해서 주변이 밝으면 색이 탁해 보인다.
- 계산 결과에는 도형을 함께 둔다. 게이지 조각 도식의 격자 한 칸은 10코 × 10단이고
  **정사각형이 아니다** — 실제 게이지 비율로 그려야 완성 모양을 보여줄 수 있다.
- ~~목록 카드의 가로 배치~~ → **정해졌다.** [BRIEF.md](BRIEF.md) §4.3이 "사진이
  있으면 더 큰 이미지형 카드로"로 답을 정했고, 그래서 실 색이 갈 자리도 정해졌다 —
  사진 아래 정보 줄의 왼쪽에 점으로 둔다. 사진 **위**에 얹지 않는 것은 편물 색이
  무엇이든 읽혀야 한다는 이 문서의 기존 규칙 때문이고, 3px 세로선을 유지하지 않는
  것은 이미지형 카드에서 그 줄이 사진의 모서리를 자르기 때문이다. **사진이 없으면
  실 색이 카드의 배경이 된다** — 그때는 가릴 사진이 없으므로 면적을 크게 쓴다.

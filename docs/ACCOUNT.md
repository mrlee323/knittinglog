# 계정과 동기화 — 기획

> 이 문서는 아직 **구현하지 않은 것**의 기획이다. 코드가 없다.

knittinglog는 계정이 없고 데이터가 기기에만 있다. 이 문서는 계정을 붙이는
기획이다. 라운지([LOUNGE.md](LOUNGE.md))가 계정을 전제로 하지만, **계정의 주
용도는 라운지가 아니라 동기화다.** 그래서 문서를 나눴다 — 동기화만 하고 라운지는
안 하는 선택이 가능해야 한다.

---

## 1. 왜 계정인가

목적이 셋이고 성격이 다르다.

| 목적 | 사용자 가치 | 위험 | 사람이 없어도 값이 있나 |
| --- | --- | --- | --- |
| **동기화** (기기 이전·여러 기기) | 큼 | 낮음 | **있다** |
| 라운지 (신원) | 중간 | 큼 (모더레이션) | 없다 |
| 결제 | 나중 | 중간 | — |

**동기화가 먼저다.** 라운지는 사람이 모이지 않으면 값이 0이지만, 동기화는
사용자 한 명에게도 즉시 값이 있다. 그리고 위험이 없다 — 모더레이션도, 법적
노출도, 빈 화면도 없다.

### 1.1 동기화가 푸는 실제 문제

- **기기를 바꾸면 몇 달치가 사라진다.** 지금은 백업 파일로 때운다(§3.13 P0).
  수동이라 잊으면 그대로 잃는다.
- **태블릿에서 도안 보고 폰에서 센다.** 실제로 원하는 사용 패턴인데 지금은
  데이터가 기기에만 있어 불가능하다.
- **브라우저 데이터를 지우면 사라진다.** `storage.persist()`로 완화했지만
  브라우저가 거절하면 방법이 없다.

---

## 2. 로그인은 선택이다 — 그러나 권한다

**앱을 열자마자 로그인을 요구하지 않는다.** 이 앱의 첫 가치는 "지금 당장 단수를
센다"이고, 그 앞에 인증 벽을 세우면 소파에서 앱을 켠 사람이 종이에 적게 된다.
기획 §5의 "계정 강제는 초기 이탈 요인"이 그 뜻이다.

그런데 **"선택이다"라고만 두는 것은 방치다.** 로그인해서 얻는 것을 앱이 그 값이
드러나는 자리에서 권해야 한다.

| 어디서 | 무엇을 권하나 |
| --- | --- |
| 설정 › 백업 카드 | "기기를 바꿔도 안 잃으려면 로그인하세요" |
| 저장 공간이 90%를 넘을 때 | "로그인하면 사진을 서버에 둘 수 있어요" |
| 데이터 보호 요청이 거절됐을 때 | 브라우저가 지울 수 있다는 경고 옆에 |
| 두 번째 기기에서 처음 열 때 | 그게 로그인의 이유 그 자체다 |
| 라운지에 들어갈 때 | 필요하므로 (LOUNGE.md) |

로그아웃해도, 계정을 지워도 **로컬 데이터는 남는다.** 백업 문서와 같은 원칙이다.

로그인 방식은 이메일 매직링크 + 애플/구글. **비밀번호는 두지 않는다** —
저장·재설정·유출 대응이 전부 우리 몫이 된다.

---

## 3. 오프라인 우선은 협상 대상이 아니다

동기화를 붙이는 순간 가장 쉽게 무너지는 것이 이것이다. 지켜야 하는 규칙.

- **쓰기는 언제나 로컬에 먼저.** IndexedDB에 쓰고 큐에 넣고, 보내는 것은 나중이다
- 네트워크가 없으면 앱은 지금과 똑같이 동작한다. 동기화만 멈춘다
- **서버 응답으로 로컬을 덮어쓰지 않는다.** 병합 규칙(§5)을 통과한 것만 반영한다
- 카운터는 서버를 기다리지 않는다. +1은 즉시 화면에 반영된다
- 마지막 동기화 시각을 보여준다. 조용히 실패하면 사용자는 안전하다고 믿는다

한 줄로: **로컬이 진실이고 서버는 사본이다.** 라운지의 "게시는 동기화가 아니다"와
같은 방향이지만, 여기서는 사본이 양방향으로 흐른다는 점만 다르다.

---

## 4. 무엇을 동기화하나

**한다**: 프로젝트·카운터·게이지·실·도안(배색·기호)·진행 기록·중단 이력·치수
프로필·스크랩·설정(언어·단위계·테마)

**안 한다**:
- **세션 중 임시 상태** — 되돌리기 스택, 지금 보고 있는 단, 화면 꺼짐 방지.
  기기에 속한 것이고 옮길 의미가 없다
- **PDF 도안의 읽던 자리** — 옮기면 좋지만 기기마다 다른 것이 자연스럽다.
  나중에 판단
- **캐시** — 서비스워커·폰트·pdf.js

---

## 5. 충돌 — 이 문서의 절반

`Base`에 `updatedAt`이 이미 있으므로 "나중에 쓴 것이 이긴다"(LWW)가 가능하다.
**그런데 전부 LWW로 하면 뜬 단수를 잃는다.** 엔티티를 성격으로 나눠야 한다.

### 5.1 카운터에 LWW를 쓰면 안 된다

태블릿에서 70단까지 뜨고, 폰에서 62단이 마지막으로 저장돼 있었다면, LWW는
저장 시각이 늦은 62를 택한다. **8단이 사라진다.** 뜨개 앱에서 이건 최악의
실패다 — 사용자가 실제로 한 노동이 없어진다.

"큰 값을 택한다"도 틀리다. −1(되돌리기)이 있으면 되돌린 것이 되살아난다.

#### 답: 카운터를 기기별 증감으로 센다 (PN-counter)

값을 스칼라로 두지 않고, **기기마다 자기가 올린 만큼과 내린 만큼**을 따로 센다.

```
counters.tally = {
  "device-a": { up: 70, down: 0 },
  "device-b": { up: 12, down: 4 },
}
현재 값 = Σup − Σdown = (70 + 12) − (0 + 4) = 78
```

- 각 기기는 **자기 칸만 늘린다.** 그래서 병합은 기기별로 큰 값을 택하면 된다 —
  물어볼 것이 없다
- +1은 내 칸의 `up`을 1 올린다. −1은 `down`을 1 올린다
- 두 기기에서 동시에 떠도 합이 맞는다

이게 카운터에 맞는 설계다. 대신 값이 파생값이 되므로 **뜨기 화면의 가장 뜨거운
경로(+1)가 바뀐다.** 그래서 §10의 단계에서 늦게 둔다.

#### 직접 수정은 별개다

앱에는 `setValue`(값을 직접 고치기)가 있다. 이건 증감이 아니라 **재설정**이라
자연히 병합되지 않는다. 재설정 기록을 하나 두고(`resetAt`, `resetTo`, 어느
기기에서) 그것만 LWW로 처리한다. 재설정 이후의 증감만 합산한다.

재설정이 두 기기에서 각각 일어난 경우는 드물고, 그때는 **묻는다**(§5.4).

### 5.2 성격별 정책

| 성격 | 엔티티 | 정책 |
| --- | --- | --- |
| 내용 문서 | 프로젝트 이름·메모, 게이지, 실, 도안 격자, 치수 프로필, 스크랩 | **LWW** (`updatedAt`) |
| 카운터 값 | `counters.tally` | **기기별 증감 합산** (§5.1) |
| 추가만 됨 | 사진, 진행 기록, 세션, 중단 이력, 마크, 실 계량 | **합집합** (id가 uuid라 충돌 없음) |
| 설정 | 언어·단위계·테마 | **LWW** — 마지막에 바꾼 기기를 따른다 |

도안 격자를 LWW로 두는 것은 안전한가? 두 기기에서 같은 도안을 동시에 편집하는
일은 드물고, 발생하면 나중 것이 이기는 게 자연스럽다. 다만 **잃은 쪽을 버리지
않는다**(§5.4).

### 5.3 삭제가 부활한다 — tombstone이 필요하다

**지금 스키마에는 삭제 기록이 없다.** 저장소에서 확인한 사실:

- 리포지토리에 하드 삭제 28곳
- `deletedAt` 같은 삭제 표시 0곳

동기화가 붙으면 이렇게 된다. 폰에서 프로젝트를 지운다 → 태블릿에는 아직 있다 →
다음 동기화에서 태블릿의 레코드가 "새로 생긴 것"으로 보인다 → **지운 것이
부활한다.**

그래서 삭제도 데이터여야 한다.

```
deletions   id · table · recordId · deletedAt · deviceId
```

또는 각 테이블에 `deletedAt`을 두고 숨긴다. **별도 테이블 쪽을 권한다** — 20개
테이블에 필드를 더하면 모든 조회에 `deletedAt is null`이 붙고, 하나만 빠뜨려도
지운 것이 화면에 나온다.

이건 **Dexie v9 마이그레이션**이고, 동기화보다 먼저 들어가야 한다. 삭제 기록이
없던 기간의 삭제는 복구할 수 없다 — 그건 받아들인다.

tombstone은 영원히 남지 않는다. **모든 기기가 받아간 뒤 90일이면 지운다.**
그 판단을 하려면 기기별 마지막 동기화 시각이 필요하다.

### 5.4 잃은 쪽을 버리지 않는다

LWW로 진 쪽을 조용히 없애면, 사용자는 무엇을 잃었는지 모른다. 뜨개 기록은
몇 달치가 쌓인 것이라 그게 아프다.

- 진 쪽 내용을 **충돌 사본으로 남긴다** (프로젝트 메모라면 메모 아래에 덧붙이는
  식으로, 도안이라면 "(충돌 사본)" 이름의 새 도안으로)
- 충돌이 있었다는 것을 알린다. 조용히 병합하지 않는다
- 사본은 사용자가 지울 때까지 남는다

물어야 하는 경우는 **카운터 재설정 충돌** 하나뿐이다. "태블릿 70단 / 폰 62단 —
어느 쪽인가요?" 실제로 이런 일은 드물다. 같은 프로젝트를 두 기기에서 동시에
뜨는 일이 드물기 때문이다(도안은 태블릿, 카운트는 폰이라 세는 기기는 하나다).
**드물기 때문에 물어봐도 괜찮다** — 자동 병합을 억지로 만들지 않는다.

## 6. 사진과 PDF — 비용은 여기서 난다

레코드는 작다. 백업 검증에서 9개 레코드가 사진 포함 18KB, 사진 없이 2.8KB였다.
**용량의 거의 전부가 사진과 PDF다.**

- 사진은 이미 `shrinkImage`로 줄여 저장한다(webp). 그걸 그대로 올린다
- **PDF는 크다** (도안 하나가 1MB+). 기본은 올리지 않고 사용자가 켠다
- 새 기기에서 로그인하면 **레코드는 즉시, 이미지는 필요할 때 받는다**(lazy).
  40장짜리 타임라인을 첫 실행에 다 받으면 데이터도 시간도 낭비다
- 그래서 **"이 기기에 없는 사진"** 상태가 생긴다. 자리표시를 보여주고, 오프라인
  이면 그렇다고 말한다. 깨진 이미지로 두지 않는다

---

## 7. 서버 데이터 모델

로컬 스키마를 그대로 옮기지 않는다. 로컬은 계속 바뀌고, 서버에 정규화하면
마이그레이션이 두 곳에 생긴다.

```
profiles      id(auth.uid) · display_name · created_at
devices       id · owner_id · label · last_synced_at
records       owner_id · table · id · updated_at · deleted_at
              · payload_json          ← 레코드 본문 그대로
files         owner_id · record_table · record_id · field · path · bytes
```

- `records`는 **테이블 이름 + id로 식별되는 봉투**다. 본문은 JSON 그대로 둔다.
  로컬 스키마가 바뀌어도 서버는 몰라도 된다
- 동기화는 `updated_at > 마지막 동기화 시각`인 것만 주고받는다
- RLS: 모든 행에 `owner_id = auth.uid()`. 남의 것은 보이지 않는다
- 카운터의 `tally`는 payload 안에 들어간다. 병합은 클라이언트가 한다 — 서버에
  병합 로직을 두면 로컬 스키마를 알아야 한다

---

## 8. 계정 삭제

- 서버의 레코드·파일을 **완전히 지운다** (soft delete가 아니다)
- **로컬 데이터는 남긴다.** 계정을 지우는 것은 서버와의 관계를 끊는 것이고,
  내 기록을 버리는 것이 아니다
- 라운지 게시물도 함께 지운다 (LOUNGE.md §10)
- 지우기 전에 백업 파일을 내려받으라고 권한다

---

## 9. 비용

Supabase 무료 티어 기준. 라운지와 달리 **전송보다 저장이 먼저 찬다** — 피드처럼
남의 이미지를 반복해 받는 일이 없기 때문이다.

| | 무료 한도 | 소비 추정 |
| --- | --- | --- |
| 저장 | 1GB | 사진 50KB × 200장 = 10MB / 사용자 |
| 전송 | 5GB/월 | 새 기기 첫 동기화에 몰린다 |
| DB | 500MB | 레코드는 작다 |

거칠게 **활성 100명까지는 무료 티어 안**이다. PDF를 켜는 사람이 많으면 그보다
빨리 찬다.

라운지와 같은 원칙: **한도 70%에서 알림이 오도록 계측을 먼저 붙인다.**

## 10. 단계

각 단계는 그 자체로 멈출 수 있어야 한다.

### 1단계 — 로그인만
Supabase Auth, 설정의 로그인/로그아웃, `ownerId` 채우기. 동기화는 없다.
→ 접어도 손해 없음. 라운지의 전제가 여기서 갖춰진다.

### 2단계 — tombstone (동기화 없이 먼저)
삭제 기록 테이블(Dexie v9). 동기화가 없어도 해가 없고, **있어야 3단계를
안전하게 할 수 있다.** 먼저 넣어두면 그 기간의 삭제가 기록으로 남는다.

### 3단계 — 한 방향 자동 백업 (기기 → 서버)
로컬이 바뀌면 서버로 보낸다. 서버에서 로컬로 오는 흐름은 없다.
복원은 지금처럼 수동(백업 파일과 같은 화면).
→ **충돌이 없다.** 그런데 "기기를 바꾸면 잃는다"는 가장 큰 문제가 이미 풀린다.
여러 기기 동시 사용만 안 된다. **값의 대부분을 위험 없이 얻는 단계다.**

### 4단계 — 양방향 동기화 (카운터 제외)
§5.2의 LWW·합집합 병합. 카운터는 아직 한 방향(기록만 올림).
충돌 사본과 알림 포함.

### 5단계 — 카운터 병합
`value` → `tally`(기기별 증감) 전환. 뜨기 화면의 +1 경로가 바뀌므로 마지막이다.

### 6단계 — 파일 lazy 동기화
사진·PDF, "이 기기에 없는 사진" 상태 처리.

---

## 11. 안 하는 것

- **실시간 협업** — 두 기기가 같은 화면을 함께 보는 것
- **한 프로젝트를 두 사람이 공유** — 권한 모델이 필요하고, 이 앱은 개인 기록장이다
- **서버가 계산하기** — 게이지·코수·검산은 로컬 도메인 함수가 한다. 서버에 두면
  오프라인에서 못 쓴다
- **웹에서 로그인해 남의 기기 데이터 보기** — 나중

---

## 12. 실패 조건

- **3단계에서 동기화 실패가 조용히 쌓이면** 되돌린다. 사용자가 백업됐다고 믿는데
  안 되어 있는 것이 백업이 없는 것보다 나쁘다. 마지막 동기화 시각과 실패 알림이
  먼저 있어야 한다
- **4단계에서 충돌 사본이 자주 생기면** 병합 규칙이 틀린 것이다. 사본이 쌓이는
  것은 사용자에게 숙제를 넘기는 것이다
- **저장이 무료 한도를 넘고 유료화 의사가 없으면** 사진 동기화를 끄고 레코드만
  올린다. 레코드만으로도 기기 이전은 된다

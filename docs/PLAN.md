# knittinglog — 기획 문서

> 하다 만 뜨개 프로젝트가 쌓여가는 사람들을 위한, 기록 중심 뜨개 워크스페이스

- 레포: `mrlee323/knittinglog`
- 문서 상태: v0.3 (2026-08-18) — §13 시각 우선 전환 추가
- 서비스명: `knittinglog` 유지 (추후 재검토 — §11 참고)

---

## 1. 문제 정의

뜨개는 한 작품 = 하나의 "프로젝트"다. 그런데 이 프로젝트들은 유독 잘 중단된다.

**왜 중단되는가**

| 원인        | 구체적 상황                                                         |
| ----------- | ------------------------------------------------------------------- |
| 맥락 유실   | 3개월 만에 꺼냈는데 몇 단까지 떴는지, 어느 도안 어디였는지 모름     |
| 물리적 점유 | 바늘이 다른 프로젝트에 물려 있어서 새 걸 못 시작하거나, 뜯어서 중단 |
| 게이지 실패 | 떠보니 사이즈가 안 맞음 → 다시 계산하기 귀찮아서 방치               |
| 실 부족     | 중간에 실이 모자란 걸 발견, 같은 로트 못 구해서 정지                |
| 가시성 없음 | 몇 개가 멈춰 있는지조차 파악이 안 됨. 죄책감만 쌓임                 |

**핵심 인사이트**
"중단"은 실패가 아니라 뜨개의 **정상 상태**다. 중단을 죄악시하는 대신
**중단해도 안전하게 돌아올 수 있는 저장소**를 만드는 게 이 서비스의 본질.

**한 줄 정의**

> 언제 멈췄든 그 자리에서 정확히 이어 뜰 수 있게 하는 뜨개 기록장.

## 2. 타깃 & 차별점

**주 사용자**

- 진행 중/중단된 프로젝트가 3개 이상인 취미 니터·크로셰터
- 도안을 사서 뜨기도 하고, 직접 변형하기도 하는 중급자
- 해외 도안을 국내 실로 옮겨 뜨는 사람 (언어·규격 장벽을 겪는 층)

**기존 서비스 대비**

| 서비스                         | 강점                 | 빈틈                                                      |
| ------------------------------ | -------------------- | --------------------------------------------------------- |
| Ravelry                        | 세계 최대 도안·실 DB | UI가 2007년. 계산기·카운터 약함. 한국어/아시아 실 DB 없음 |
| Knit Companion, Row Counter 류 | 카운터 특화          | 프로젝트 관리·계산과 단절된 단일 도구                     |
| Stitch Fiddle                  | 차트 에디터          | 기록과 단절. 게이지 반영 안 됨                            |

**우리 차별점**

1. **카운터·도안·게이지·실이 하나의 프로젝트 안에서 연결됨** — 도구가 아니라 작업대
2. **"중단 관리"를 1급 기능으로** — 잠시멈춤 상태, 복귀 브리핑, Lifeline, 방치 리포트
3. **게이지 → 도안 자동 리사이징** — 계산이 귀찮아 포기하는 지점을 제거
4. **언어 중립 도안 모델** — 한↔영↔일 도안 상호 변환 (§4). 처음부터 글로벌 설계
5. 대바늘·코바늘 동등 지원, 국가별 실 굵기·바늘 호수 규격 대응

## 3. 전체 기능 맵

`P0` = MVP, `P1` = 2차, `P2` = 3차, `P3` = 장기.

### 3.1 프로젝트 (작품) 관리 — `P0`

- 프로젝트 CRUD: 이름, 기법(대바늘/코바늘), 종류(스웨터/모자/양말/숄/가방/소품/담요), 대상(나/선물), 시작일
- **상태 머신**: `계획중` → `진행중` → `잠시멈춤` → `완성` / `풀어버림`
  - 잠시멈춤(hibernating)은 부정적 상태가 아님. 중단 사유를 함께 기록
  - 중단 사유 태그: `실부족` `게이지실패` `싫증` `난이도` `바늘뺏김` `시즌아님` `기타`
- **복귀 브리핑** — 프로젝트 열면 상단에 자동 요약
  - "마지막 작업: 4개월 전 · 몸판 앞판 62단/120단 · 4.0mm 줄바늘 80cm
    · 실 잔량 2.3타래 · **마지막 생명줄 48단** · 마지막 메모: 진동 줄임 직전"
- 사진 타임라인 (진행 사진 + 날짜)
- 프로젝트 일지 (날짜별 자유 메모)
- 프로젝트 ↔ 도안 / 실 / 바늘 / 게이지 / 카운터 연결
- 완성 기록: 완성일, 최종 치수, 총 소요 시간, 완성 사진, 후기·개선점

### 3.2 카운터 (단수 세기) — `P0`

뜨는 동안 실제로 손에 쥐고 쓰는 화면. **오프라인 필수, 오조작 방지 필수.**

- 다중 카운터: 한 프로젝트에 여러 개 (몸판 / 소매 / 무늬반복 / 코수)
- **연동 카운터**: 메인 8단마다 서브 +1 (배수 링크)
- 목표 단수 → 진행률 바, 남은 단수
- 반복 구간: "12단 무늬 × 5회" — 현재 몇 회차 몇 단인지 표시
- 화면 절반 이상을 차지하는 큰 +1 히트 영역, 햅틱 피드백
- 실행 취소(오탭 복구), 길게 눌러 −1
- **화면 꺼짐 방지** (Wake Lock API)
- 단수별 메모 핀 ("여기서 마커 이동", "여기서 실 교체")
- **Lifeline(생명줄) 마크** → §3.10
- 세션 타이머: 카운터를 여는 순간부터 뜬 시간 자동 측정
- 도안/차트 연결 시 현재 단 자동 하이라이트 (§4 IR 기반)

### 3.3 게이지 — `P0`

이 서비스의 계산 엔진 핵심.

- 게이지 스와치 기록: 실, 바늘 호수, 무늬, 세탁 전/후 수치, 사진
- 10cm(4inch) 기준 코수·단수 저장
- **치수 ↔ 코수 변환기**: "가슴둘레 96cm 필요 → 몇 코?"
- **도안 리사이징** — 핵심 기능
  - 입력: 도안 게이지, 내 게이지, 도안 원본 코수/단수/증감 위치
  - 출력: 내 게이지 기준 재계산된 코수·단수·증감 배치
  - 무늬 배수 보정 (4코 1무늬면 4의 배수로 반올림)
- 블로킹 수축률(blocking factor) 반영
- 게이지가 안 맞을 때 바늘 호수 조정 제안
- **바늘 호수 환산표**: mm ↔ JP호 ↔ US ↔ UK (대바늘/코바늘 별도 체계)

### 3.4 실 (Yarn) 관리

- **스태시** `P0`: 브랜드, 제품명, 색상명·색번, **로트번호**, 구성(울/면/알파카…), 굵기, 타래 무게(g), 타래 길이(m), 보유 타래 수, 사진, 구매처·가격·구매일, 세탁 라벨
- 프로젝트에 실 할당 → 사용량 차감, 잔량 추적 `P0`
- **국가별 실 굵기 대조표** `P0` → §3.10
- **실 부족 예측 (Yarn Chicken)** `P1` → §3.10
- **실 소요량 계산기** `P1`: 필요 미터 ↔ 그램 환산, 다른 실로 바꿀 때 필요 타래 수
- 실 대체(substitution) 추천: 굵기·게이지·구성 유사도 기반 `P2`
- **실 라벨 OCR / 바코드 스캔** `P3` → §3.10
- 자투리 실 관리, 자투리로 뜰 수 있는 소품 추천 `P3`

### 3.5 바늘·도구 — `P1`

- 바늘 인벤토리: 호수, 길이, 재질, 종류(막대/줄/장갑/코바늘)
- **점유 상태**: "4.0mm 80cm 줄바늘 = 현재 회색 스웨터에 물려 있음"
  → 새 프로젝트 시작 시 바늘 충돌 경고 (중단의 실제 물리적 원인)
- 기타 도구: 마커, 돗바늘, 게이지자

### 3.6 도안 (Pattern) — `P1`

> 저장 형식은 §4 IR을 따른다. 아래는 사용자에게 보이는 기능.

- 도안 보관함: PDF 업로드 / 외부 URL 링크 / 직접 작성
- PDF 뷰어 + **읽던 위치·줄 하이라이트 저장**
- **IR 네이티브 도안 에디터** — 코 단위로 단을 조립 (파싱 불필요, 정확)
- 기존 텍스트 도안 → IR 파싱 (약어 인식 + 사용자 확인 UI) `P2`
- 단계별 체크오프 + 카운터 자동 연동
- 사이즈 표기 파싱 — `S(M, L, XL)` 괄호 표기에서 **내 사이즈만 하이라이트**
  (도안 읽다 사이즈 헷갈려 틀리는 사고가 잦음)
- 도안 수정 기록: "원 도안 대비 내가 바꾼 부분" 별도 관리
- 도안 출처·가격·저작권 메모

### 3.7 도안 그리기 (차트 에디터) — `P2` · 차별화 포인트

- 그리드 캔버스 + 심볼 팔레트 (표준 심볼셋)
- **대바늘 차트 / 코바늘 차트** — 코바늘은 원형·모티브 자유 배치라 별도 렌더러
- **색상 차트**(페어아일/인타르시아): 팔레트 기반 픽셀 도안
- **이미지 → 색상 차트 변환**: 사진 업로드 → 색 양자화 → 그리드 생성
- 반복 구간(repeat box) 지정
- **게이지 비율 렌더링**: 뜨개 코는 정사각형이 아님. 실제 가로:세로 비를 적용한
  "완성 시 실제 모양" 미리보기 (기존 차트 앱 대부분이 실패하는 지점)
- **차트 ↔ 서술형 도안 상호 변환** — 같은 IR의 두 렌더러 (§4)
- 좌우 반전 / 회전 (왼손잡이, 반대쪽 소매)
- 내보내기: PNG / PDF / 공유 링크
- 차트를 카운터에 연결해 뜨면서 따라가기

### 3.8 뜨개 계산기 모음 — `P1`

각각 독립 실행 가능하고, 프로젝트 게이지와 **신체 치수 프로필**(§3.10)을 자동으로 물어온다.

| 계산기           | 내용                                    |
| ---------------- | --------------------------------------- |
| 균등 증감        | N코를 M코로 균등하게 늘리기/줄이기 배치 |
| 목선·암홀 곡선   | 코막음 배분 (3-3-2-2-1-1 …)             |
| 래글런           | 래글런 증가 단·코 배분                  |
| 원형 요크        | 요크 증가 회차별 배분                   |
| 소매             | 소매산·진동 배치                        |
| 양말             | 발볼·발길이 → 코수, 뒤꿈치 배분         |
| 모자             | 머리둘레 → 코수, 크라운 감소 배분       |
| 숄               | 삼각/반원 증가 규칙 생성                |
| 단춧구멍         | 단추 개수 → 균등 위치 배분              |
| 허리 다트        | 허리 조절 증감 배치                     |
| 코바늘 원형      | 원형 시작 증가 규칙                     |
| 평면 ↔ 원형 변환 | 겉/안 반전 + 단 방향 전환 (§4 IR 기반)  |
| 단위 환산        | cm↔inch, g↔oz, m↔yd, 바늘 호수, 실 굵기 |

### 3.9 기록 · 통계

- 뜨개 일지: 날짜별 뜬 시간·단수 자동 집계 (카운터 세션에서 파생) `P0`
- 대시보드: 진행중 N개 / 잠시멈춤 N개 / 올해 완성 N개 `P0`
- 누적 통계: 총 뜬 단수, 총 시간, 소비한 실 길이(m)·무게(g), 완성 작품 수 `P0`
- **잔디 히트맵**: 날짜별 뜨개 활동량 (GitHub 컨트리뷰션 스타일) `P1`
- **푼 기록(frogging log)** `P1` → §3.10
- **방치 리포트** `P1`: 오래 멈춘 프로젝트 + 중단 사유 분포
  → "당신은 주로 '게이지 실패'로 멈춥니다" 같은 자기 인식 제공
- **완성 예상일** `P1` → §3.10
- 연간 결산 카드 (공유 가능) `P2`

### 3.10 추가 확정 기능

기존 기능들과 교차하는 8개 항목. 소속 영역이 여러 곳이라 여기 모아둔다.

#### (1) 신체 치수 프로필 — `P0`

- 내 치수 저장: 가슴/허리/엉덩이/어깨너비/팔길이/팔둘레/등길이/머리둘레/발길이·발볼
- **여러 프로필 관리** — "나", "엄마", "조카" (선물용 프로젝트가 많음)
- 모든 계산기가 프로필을 자동으로 물어옴. 매번 재는 귀찮음이 이탈 지점
- 여유분(ease) 설정: 실측 + 여유 = 완성 치수 (핏 취향을 −5cm~+15cm로)

#### (2) Lifeline(생명줄) 기록 — `P0` · **시그니처 기능**

- 생명줄을 넣은 단수를 카운터에서 원탭 기록
- 복귀 브리핑·카운터 상단에 "마지막 생명줄: 48단" 상시 표시
- 실수해도 여기까지만 풀면 된다는 **안전선**. 서비스 컨셉("멈춰도 안전")과 동일 철학
- 생명줄 넣을 때 그 시점 코수도 함께 스냅샷

#### (3) 실 부족 예측 (Yarn Chicken) — `P1`

- 남은 실 무게를 저울로 재서 입력 → 지금까지 뜬 단수로 **단당 소모량 역산**
- "남은 40단 필요한데 실은 32단치" 경고
- 실 부족은 중단 사유 상위권인데 현재는 **터지고 나서야** 안다. 이걸 미리 알림
- 부족 시 대응 안내: 다른 로트 교대로 섞어 뜨기(alternating rows), 배색 전환

#### (4) 완성 예상일 — `P1`

- 카운터 세션에서 개인 뜨기 속도(단/시간) 학습 → 남은 단수로 완성일 추정
- 데드라인 설정 시 필요 페이스 역산 ("하루 18단 떠야 크리스마스 도착")
- 선물 프로젝트 데드라인 관리와 직결

#### (5) 국가별 실 굵기 대조표 — `P0` · **글로벌 필수**

- 미국(CYC 0~7) ↔ 영국/호주(ply) ↔ 일본(합태·중세) ↔ 한국 명칭 대조
- 굵기별 권장 게이지·바늘 호수 범위
- 단위계 전역 전환: metric(cm/g/m) ↔ imperial(inch/oz/yd)
- **이게 없으면 해외 도안을 국내 실로 못 뜬다.** 정적 데이터라 구현 비용은 낮음

#### (6) 실 라벨 OCR / 바코드 스캔 — `P3`

- 실 라벨 사진 → 브랜드·구성·굵기·게이지·로트번호·세탁기호 자동 입력
- 스태시 등록이 가장 귀찮은 작업이라 여기가 실질적 이탈 지점
- 바코드 스캔으로 상용 실 DB 조회 (DB 확보 후)

#### (7) 스티치 사전 — `P1`

- 기법별 설명 + 도해 + 영상 링크
- **§4 IR의 op 집합과 1:1 연결** — 도안 어디서든 약어를 탭하면 사전이 열림
- 다국어 명칭 병기 (사전 자체가 §4 로케일 사전의 사용자용 뷰)

#### (8) 푼 기록 (Frogging Log) — `P1`

- 푼 단수·사유·날짜 기록. 통계에서 "뜬 단수" 옆에 "푼 단수"
- 방치 리포트의 재료. "이 프로젝트는 3번 풀었다" = 난이도 신호
- 심리적 효과: 푼 것도 노동이었다는 걸 인정해줌

### 3.11 AI 기능 — `P3`

- **게이지 사진 인식**: 스와치 사진 + 기준 스케일 → 코수·단수 자동 카운트
  - 완전 자동은 정확도 리스크가 큼. **반자동 권장**:
    사용자가 10cm 사각형 네 꼭짓점을 찍고 → 그 안의 코·단만 추정 → 사용자 보정
- 도안 PDF → IR 구조화 파싱 (LLM 보조 + 사용자 확인)
- 완성 사진 → 프로젝트 종류·색상 자동 태깅

### 3.12 공유 · 커뮤니티 — `P3`

- 내 작품 갤러리 공개 링크 (읽기 전용)
- 도안 공유 / 판매
- 같은 도안을 뜬 사람들의 **실제 게이지 분포** — 실사용 가치가 매우 큼
- 뜨개 모임(knit night), 같이 뜨기(KAL)

### 3.13 플랫폼 · 기반 — `P0`

- **PWA · 오프라인 우선** — 카운터는 인터넷 없이 100% 동작해야 함
- 로컬 우선 저장(IndexedDB). 서버 동기화는 2차
- **i18n 기반 구조** — UI 문자열 + §4 도안 로케일 사전. 1차는 ko/en
- 다크 모드
- 모바일 우선 반응형 (실사용의 90%가 소파에서 폰)
- 데이터 내보내기 (JSON/CSV) — 락인 없음

## 4. 도안 표현 모델 (IR) — 아키텍처 중심축

이 서비스를 글로벌로 만드는 핵심 결정. **도안을 텍스트가 아니라 언어 중립 구조로 저장한다.**

### 4.1 왜

한→영 도안 번역을 기계번역으로 하면 반드시 깨진다.
`k2tog` ↔ `오른코모아뜨기`는 번역이 아니라 **기호 변환**이기 때문이다.

### 4.2 어떻게

```
저장:  "k2, yo, k2tog, p1"        (X)
저장:  "겉2, 바늘비우기, ..."      (X)
저장:  [{op:"knit",n:2},
        {op:"yo"},
        {op:"k2tog"},
        {op:"purl",n:1}]          (O)
```

표시할 때만 **로케일 사전**을 통해 렌더링한다.

| IR                | ko             | en    | ja          | fr          |
| ----------------- | -------------- | ----- | ----------- | ----------- |
| `{op:"knit",n:2}` | 겉 2코         | k2    | 表目2目     | 2 m end     |
| `{op:"k2tog"}`    | 오른코모아뜨기 | k2tog | 右上2目一度 | 2 m ens end |
| `{op:"yo"}`       | 바늘비우기     | yo    | かけ目      | 1 jeté      |

**번역 = `파싱(원본 언어) → IR → 렌더링(대상 언어)`.**
기계번역이 아니라 결정적 변환이므로 틀릴 수 없다.
새 언어 추가 = **사전 파일 하나**. 코드 수정 없이 일본어·프랑스어·스페인어로 확장.

### 4.3 IR 하나가 만들어내는 파생 기능

이 모델을 채택하면 아래가 전부 같은 데이터의 다른 뷰가 된다.

| 기능                    | 구현                                                     |
| ----------------------- | -------------------------------------------------------- |
| 다국어 도안             | 로케일 사전 렌더러                                       |
| 차트 ↔ 서술형 상호 변환 | 같은 IR의 그리드 렌더러 / 텍스트 렌더러                  |
| **자동 검산**           | 각 단의 코수를 IR에서 계산 → 도안 오류 검출              |
| 카운터 연동             | 단별 IR을 카운터에 주입 → "지금 이 단은 뭘 하는 단" 표시 |
| 평면 ↔ 원형 변환        | 겉/안 op 스왑 + 단 방향 반전                             |
| 좌우 반전               | op 순서 반전 + 좌우 대응 op 스왑(k2tog↔ssk)              |
| 게이지 리사이징         | 반복 구간이 구조로 있어 코수 재계산이 정확               |
| 스티치 사전             | op 집합이 곧 사전 표제어                                 |

**자동 검산이 특히 크다.** "이 단이 끝나면 62코여야 하는데 도안대로 세면 61코"를
잡아낸다. 도안 오탈자로 몇 시간 날린 경험은 니터라면 대부분 있다.

### 4.4 대바늘 · 코바늘

op 집합을 craft별로 분리하되 같은 IR 틀에 넣는다.

- **대바늘**: `knit` `purl` `yo` `k2tog` `ssk` `sl` `psso` `cable(n, dir)` `m1l` `m1r` …
- **코바늘**: `ch` `sc` `dc` `tr` `slst` `inc` `dec` `magic-ring` `into(target)` …
  - 코바늘은 "어디에 뜨는가"(전단 어느 코/공간)가 필수 정보라 `into` 슬롯이 추가된다
  - 원형·모티브는 격자가 아니라 **극좌표 배치**라 차트 렌더러가 별도

### 4.5 현실적 단계

1. `P1` — **IR 네이티브 에디터**부터. 사용자가 코 단위로 조립 → 파싱 문제 없음
2. `P1` — 로케일 사전 ko/en + 렌더러 + 자동 검산
3. `P2` — 기존 텍스트 도안 파서 (규칙 기반 + LLM 보조 + 사용자 확인 UI)
4. `P2` — 차트 렌더러 (IR ↔ 그리드)
5. `P3` — PDF 도안 자동 구조화

파싱이 어려운 것이지 번역·변환은 어렵지 않다. **어려운 쪽을 뒤로 미루고
쉬운 쪽(에디터·렌더러)부터 가면 IR의 가치를 일찍 확보할 수 있다.**

## 5. 1차 개발 범위 (MVP)

**목표: "하다 만 프로젝트"를 안전하게 담고 다시 꺼낼 수 있는 최소 제품**

### 포함 (P0)

1. 프로젝트 관리 + 상태 머신 + 중단 사유 + 사진 타임라인 + 복귀 브리핑
2. 카운터 (다중·연동·목표·메모·**Lifeline**·오프라인·화면유지·타이머)
3. 게이지 기록 + 치수↔코수 변환 + 도안 리사이징 + 바늘 호수 환산
4. 실 스태시 기본 + 프로젝트 할당·잔량 + **국가별 굵기 대조표**
5. **신체 치수 프로필** (다중 프로필 + 여유분)
6. 대시보드 기본 통계
7. PWA / 오프라인 / 다크모드 / 모바일 우선 / **i18n 골격(ko·en)** / 단위계 전환

### 제외 (의도적)

- **로그인 없음** — 1차는 로컬 전용 무계정. 계정 강제는 초기 이탈 요인.
  Supabase는 2차에 "백업·기기간 동기화" 기능으로 붙인다.
  (설계 시 나중에 계정을 얹을 수 있도록 데이터에 `ownerId` 자리를 비워둘 것)
- 도안 IR·에디터, 차트 에디터, 계산기 모음, 커뮤니티, AI 인식
- 실 부족 예측 / 완성 예상일 / 푼 기록 / 스티치 사전 (P1)

### MVP 완료 기준

- 프로젝트 5개를 등록하고 그중 2개를 중단 상태로 둔 뒤,
  3개월 뒤 열었을 때 **어디서부터 이어 뜰지 30초 안에 파악 가능**하다.
- 비행기 모드에서 카운터가 완전히 동작하고, 앱을 껐다 켜도 단수가 보존된다.
- 영어 UI로 전환해도 전 화면이 깨지지 않는다.

## 8. 기술 방향

### 현재 레포 스택 (유지)

Vite 7 · React 19 · TypeScript 5.9 · Tailwind 4 · TanStack Query ·
Jotai · XState 5 · Zod 4 · Supabase(2차) · lucide-react · husky/lint-staged/prettier

### 라우터: **TanStack Router** (확정)

- 이미 TanStack Query가 스택에 있어 정합성이 좋음
- **타입 안전 search params** — 프로젝트 목록의 필터·정렬 상태를 URL에 그대로 담기 좋음
- 파일 기반 라우팅 + 자동 코드 스플리팅
- 트레이드오프: React Router보다 생태계가 작고 Vite 플러그인 설정이 한 단계 더 필요

### 매핑

| 도구           | 용도                                                     |
| -------------- | -------------------------------------------------------- |
| XState         | 프로젝트 상태 머신, 카운터 상태 머신(연동·반복·실행취소) |
| Jotai          | 카운터 실시간 로컬 상태, UI 상태                         |
| TanStack Query | 로컬 DB 쿼리 캐싱 → 2차에 서버 동기화로 확장             |
| Zod            | 도안 IR 스키마 검증, 입력 검증, 내보내기 스키마          |
| Supabase       | 2차: 인증·DB·스토리지(사진)                              |

### 추가 필요

- **로컬 저장소**: Dexie (IndexedDB) — 오프라인 우선의 근간
- **PWA**: `vite-plugin-pwa`
- **라우팅**: `@tanstack/react-router` + Vite 플러그인
- **i18n**: 경량 자체 구현 또는 `i18next` — UI 문자열과 §4 도안 사전은 **분리**할 것
- **차트 캔버스** (P2): Canvas 2D 직접 구현 (라이브러리 의존 최소화)
- **이미지 처리** (P2/P3): 브라우저 Canvas + 색 양자화 직접 구현

### 초기화 작업

기존 보일러플레이트의 **구조·디자인은 전부 걷어낸다.**

- 제거: `src/App.tsx`, `src/App.css`, `src/assets/react.svg`, `public/vite.svg`
- 재작성: `src/index.css` → Tailwind 4 + 디자인 토큰만
- 재작성: `README.md` → 프로젝트 소개
- 재설계: `src/` 디렉터리 구조 (feature 기반)
- 유지: `src/lib/utils.ts`, `src/components/providers.tsx`,
  `src/lib/supabase.ts`(2차용, 미사용 보관), 툴링 설정 일체

### 제안 디렉터리 구조

```
src/
  app/            라우터, 프로바이더, 레이아웃
  features/
    project/      도메인 로직 + UI + 상태머신
    counter/
    gauge/
    yarn/
    profile/
    stats/
    pattern/      (P1) IR 에디터·렌더러
  components/ui/  공용 프리미티브 (버튼, 시트, 다이얼로그…)
  domain/         ★ 순수 계산 함수 — UI 무관, 테스트 대상
    gauge.ts        게이지 변환·리사이징
    shaping.ts      증감·곡선 배분
    yarn.ts         소요량·잔량 예측
    units.ts        단위·호수·굵기 환산
    pattern/        IR 타입, 검산, 변환(평면↔원형, 반전)
  i18n/
    ui/             UI 문자열 (ko, en)
    stitches/       ★ 도안 op 로케일 사전 (ko, en, …)
  lib/            db(Dexie), 포맷터
  types/
```

`domain/`을 UI와 분리하는 것이 중요하다. 뜨개 계산은 순수 함수이고
**정확도가 곧 신뢰도**이므로 단위 테스트를 붙일 수 있는 형태로 격리한다.
현재 테스트 러너가 없으므로 **Vitest 도입 필요**.

## 9. 디자인 방향 (초안)

- **뜨는 중 화면**은 완전히 다른 규칙: 큰 터치 타깃, 최소 정보, 고대비, 한 손 조작
- 관리 화면은 **사진이 주인공** — 뜨개는 시각적 취미. 카드형 그리드
- 톤: 실·섬유의 질감을 연상시키는 따뜻한 뉴트럴 + 포인트 한 색
- 다크 모드 필수 (밤에 뜨는 사람이 많음)
- 폰트: 숫자 가독성 최우선 (단수·코수가 핵심 정보) — tabular numerals
- **다국어 레이아웃 내성**: 독일어·프랑스어는 한국어보다 2~3배 길다.
  버튼·라벨을 고정폭으로 짜지 말 것

| 기법 범위 | **대바늘 + 코바늘 모두**                                            |
| 추가 기능 | §3.10 8개 항목 전부 채택                                            |

## 11. 남은 이슈

**서비스명** — `knittinglog`으로 가되, 다음을 인지하고 있을 것:
영어권에서 *knitting*은 대바늘만 뜻하고 코바늘(crochet)은 포함하지 않는다.
코바늘을 동등하게 지원하기로 한 이상, 글로벌 확장 시점에 크로셰터가
"내 서비스가 아니다"라고 판단할 여지가 있다. 리브랜딩한다면 craft 중립 이름
(Stitchbook / Loop / Unwind 등)을 검토. 레포명 변경은 언제든 가능하므로
지금 막지 않고, **UI 상의 표기명만 나중에 분리**할 수 있게 설계해둔다.

## 13. 시각 우선 전환 (v0.3 방향)

`P0`가 다 돌아가는데도 "다른 앱에도 다 있는 기능"으로 읽혔다. 진단은 두 가지다.

1. **화면이 사무용이다.** 공용 프리미티브가 `field`·`page`·`button`뿐이었다.
   기획은 "사진이 주인공"이라 적어두고 사진 화면을 안 만든 상태였다.
2. **차별점으로 적어둔 것들이 미구현이다.** 언어 중립 IR(§4)과 차트(§3.7)는
   이 문서가 스스로 최대 무기라 규정했는데 `P2`로 밀려 있다.

그래서 다음 순서는 "기능 추가"가 아니라 **같은 데이터를 그림으로 보여주기**다.
뜨개는 보이는 게 중요한 취미이고, 하루에 실제로 열리는 화면은 뜨기 모드 하나다.

### 13.1 착수한 것

| 항목                | 핵심                                                                      |
| ------------------- | ------------------------------------------------------------------------- |
| 작품 사진           | 마지막 모습을 크게 + 찍은 시점의 **단수 스탬프**. 앨범이 아니라 복귀 수단 |
| 게이지 조각 도식    | 계산 결과를 선도로 그린다. 격자는 10코×10단이고 **정사각형이 아니다**     |
| 같은 작품 다시 뜨기 | 카운터 구성·게이지를 이어받고 실만 새로 고른다                            |

### 13.2 다음 (결정된 것)

**게이지 사진 측정** _(구현됨)_ — 자동 인식이 아니다. 사진에 크기를 아는 물체(자·신용카드
85.6mm·500원 26.5mm)를 함께 찍으면 픽셀↔cm 환산이 결정된다. 사용자가 코를 세고
(20코) 앱이 재는 구조 — **CV가 아니라 산수다.** 촬영 후 정지 화면에서 막대를
양끝에 맞추고 자 눈금 두 점을 탭한다. 코수는 고정하지 않는다(굵은 실은 20코가
화면을 넘고, 가는 실은 40코로 재면 오차가 절반이 된다). 자동 추정(자기상관)은
나중에 "대충 맞춰주기" 편의로만 얹는다.

**문양 렌더러** _(①②③④ 구현됨)_ — §3.7을 쪼개서 시작한다: ① 색상 차트(픽셀 도안) → ② 게이지
비율 미리보기 → ③ 사진→색상 차트 변환 → ④ 무늬 심볼. ②까지만 해도 정사각형
격자로 거짓말하는 기존 차트 앱과 갈라진다.

④에서 §4의 IR이 처음 실제로 쓰였다. 칸에 색이 아니라 기법(op)을 담으면 코수
변화(`consumes`/`produces`)가 따라오고, 거기서 세 가지가 공짜로 나온다.

- **코수 자동 검산.** 각 단이 먹는 코수가 전단이 남긴 코수와 맞는지 계산이
  본다. 9코 반복 무늬를 20코에 얹으면 뜨기 전에 알려준다. 손으로 세다 놓치면
  몇 시간 뜬 뒤에 알게 되는 종류의 실수다.
- **한↔영 서술형 변환.** 같은 격자에서 `겉 1코, 바늘비우기, 오른코모아…`와
  `k1, yo, k2tog…`가 나온다. 기계번역이 아니라 결정적 기호 변환이다.
- **뜻이 맞는 좌우 반전.** 격자만 뒤집으면 기울기가 반대인 무늬가 나온다.
  기운 코는 대응되는 코로 바꾼다(k2tog ↔ ssk, m1l ↔ m1r). 색에는 기울기가
  없어서 색상 차트에는 없던 문제다.

구조도 이때 갈랐다 — **코수 변화는 `domain/stitches.ts`가, 이름은
`i18n/stitches`가 소유한다.** 한 파일에 두면 언어를 추가할 때 검산 표를
건드리게 되고, 그 반대도 마찬가지다.

**평면 뜨기 서술형 변환** _(구현됨)_ — 원형만 지원하던 제약을 풀었다. 평면은 매 단
뒤집으므로 안면 단에서 두 가지가 함께 바뀐다: 읽는 방향이 왼쪽→오른쪽이 되고,
**그려진 기호를 그대로 뜨면 안 된다.** 도안은 겉에서 본 모습이므로 겉뜨기 기호를
안뜨기로 떠야 겉에서 겉뜨기로 보인다. 방향만 뒤집으면 반만 맞는 도안이 되는데,
그건 없는 것보다 나쁘다.

그래서 기법 표에 `ws`(안면에서 실제로 뜨는 기법)를 더했다. `겉→안`, `안→겉`,
`k2tog→p2tog`, `ssk→ssp` 같은 대응이고, 안면 전용 기법 8개(p2tog·ssp·p3tog·
sssp·cddp·m1lp·m1rp·pfb)가 함께 들어왔다. 이 기법들은 **도안에 그려지지 않는다** —
격자는 늘 겉에서 본 모습이므로 기법 선택 목록에서 뺀다(`chartOps`).

**표가 이 작업의 위험 지점이다.** 기울기 대응이 뒤바뀌면 완성품의 기울기가 반대로
나오는데, `p2tog`와 `ssp`의 delta가 같아서 **코수 검산으로는 잡히지 않는다.**
그래서 불변식 두 개를 테스트로 못 박았다.

- 그릴 수 있는 모든 기법에 `ws` 대응이 있다 — 새 기호를 더하면서 안면 동작을
  정하지 않으면 테스트가 걸린다. 안 그러면 평면 서술형이 조용히 겉면 기법을 낸다.
- `ws` 대응의 delta가 기호와 같다 — 어긋나면 평면 도안의 코수 검산이 틀린 값을
  조용히 낸다.

부수 효과로 실제 도안의 관습이 공짜로 나왔다. 홀수 단만 무늬가 있고 짝수 단은
기호가 전부 겉뜨기인 레이스 차트를 평면으로 두면 짝수 단이 `안 9코`로 렌더된다 —
도안이 흔히 "안면 단은 전부 안뜨기"라고 적어두는 그 관습이다.

1단을 안면부터 시작하는 도안도 있어 시작 면을 고를 수 있게 뒀다. §4의 평면↔원형
**변환**(같은 무늬를 평면용/원형용으로 바꿔 쓰기)은 아직 남은 과제다.

**PDF 도안** _(구현됨)_ — 상용 도안은 대개 PDF로 온다. 뜨는 동안 읽는 문서이므로
이미지 도안과 같은 요구가 붙는다(확대·이동) + 페이지와 **읽던 자리**가 더해진다.
40쪽짜리 도안에서 매번 찾아 들어가는 것은 중단의 비용을 그대로 물리는 일이라,
넘긴 페이지와 확대율을 남겨 덮어둔 자리에서 다시 열린다. 작업대·뜨기 모드의
같은 항목 목록에 들어가므로 "도안 보면서 카운팅"이 그대로 된다.

pdf.js를 쓰되 **프리캐시에서 뺐다.** 본체 420KB + 워커 1MB인데, PDF를 넣지 않는
사람에게 설치할 때 받게 할 이유가 없다(Pretendard 서브셋과 같은 판단). 오프라인은
그래도 성립한다 — PDF를 읽으려면 먼저 넣어야 하고, 넣을 때 페이지 수를 세면서
캐시에 남는다. 프리캐시는 845 → 853KiB로 8KiB만 늘었다.

표준 14폰트 데이터와 CJK cmaps도 함께 얹었다. Helvetica·Times는 PDF에 내장되지
않는 경우가 많고, 그때 pdf.js가 이 파일들을 골라 받는다. 없으면 시스템 서체로
어림잡아 대체되어 자간·줄바꿈이 원본과 달라지는데, 도안에서는 그게 "몇 코"가
몇 번째 줄에 있는지를 바꿀 수 있다.

**영감 보관함** — 핀터레스트·Threads의 저장 항목을 API로 읽는 길은 막혀 있다
(OAuth 심사·서버 필요, Threads는 저장 항목 API가 없다). 대신 **Web Share Target**
으로 PWA를 공유 대상에 등록한다. 서버·심사 없이 안드로이드에서 동작하고,
영감 카드를 프로젝트에 연결하면 상세 화면이 무드보드가 된다(iOS Safari 미지원 —
붙여넣기 경로로 대체).

### 13.3 방향을 바꾼 것

**"안 세도 되는" 카운터.** 이어폰 버튼·페달 같은 입력 장치는 결국 손을 쓰고
장비가 필요하다. 더 쉬운 쪽은 세는 행위 자체를 줄이는 것이다 —
`domain/stats.ts`의 `rowsPerHour`로 세션 시간에서 단수를 추정해 한 번 확인받고,
반복 구간은 "무늬 1회 완료" 한 탭으로 12단을 올리고, 놓친 구간은 사진으로
복구한다(게이지 사진 측정과 같은 엔진). 음성 인식은 Chrome이 서버를 타서
비행기 모드에서 죽으므로 후보에서 뺀다.

**커뮤니티는 열지 않는다.** 계정·모더레이션·임계질량이 필요한데 그 시장은
Ravelry와 인스타가 갖고 있다. 대신 내 프로젝트·게이지·차트를 **카드 이미지로
내보내기**만 만든다. 공유는 우리가 만들고 커뮤니티는 남의 플랫폼에 둔다 —
영감 보관함과 같은 인프라를 쓴다.
